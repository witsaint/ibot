# 对外服务与外部入口：产品结构、功能与接入流程

日期：2026-10-13。状态：待开发产品方案。本文将个人 bot 的外部入口细化到功能、页面、操作和联调；没有配置真实飞书应用、生成密钥、发消息或修改现有自动化执行逻辑。

## 1. 提供什么

i-bot 是支持多位用户使用的平台。其他人可以拥有独立平台账号、创建自己的 bot、连接自己的账号并管理自己的服务。每个 bot 的私人会话、电脑和凭据仍按所有权保护；平台允许多人使用不等于每个 bot 向所有用户开放。

用户在自己 bot 下创建外部入口，开放明确业务能力。同事可以经飞书使用该服务，也可以另有自己的 i-bot 平台账号；服务调用不自动获得所有者的 bot 工作区、电脑或私人对话访问权。未来若提供平台内的服务使用页面，也只开放已获准业务，不复用所有者私人聊天。

一个 bot 可以有多个入口，例如“需求助手 → Triage”“客户事件 → Webhook”。一个入口绑定明确来源、开放能力、输入和结果、资源及业务账号、调用权限和运行规则。bot 停用或入口关闭后停止接受相应新请求；停止已运行任务另行处理。

首期支持：

| 功能           | 用户能配置/查看什么                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------- |
| 开放能力       | 从已启用且具备外部执行支持的插件/工具选择查询、创建等业务动作；定义输入、结果、固定参数与需要补充的字段 |
| 绑定来源       | 已运行飞书机器人转交、新接入独立飞书应用、普通 webhook                                                  |
| 调用权限       | 外部人员或已核验服务身份可调用哪些动作；可用部门资料时按部门配置                                        |
| 业务资源与账号 | 允许的团队/项目、动作使用的业务连接、结果允许交付的目标                                                 |
| 运行控制       | 启停、排队、额度、频率、预算、超时及需本人处理的条件                                                    |
| 联调           | 接入检查、权限模拟、示例事件、真实受控测试及失败原因                                                    |
| 记录           | 接收、权限判断、执行、人工等待及结果投递分别记录；重复事件和重试可追踪                                  |

不是将整个个人聊天 API 开放。外部任务不能任意选择个人插件、修改入口规则或要求读取本人浏览器；它只能调用入口已开放能力。能力中的说明可辅助 agent 处理任务，但实际工具与资源约束由服务端执行。

## 2. 整体产品结构与页面入口

推荐把对外服务做成 i-bot 内的独立管理模块，使用平台账号和权限，提供完整页面及固定地址。每位用户看到自己有权管理的服务、任务和连接。首期不另建域名、账号体系或公司后台。服务端接收和执行必须持续在线，不能依赖管理页面、聊天窗口或 sandbox 网页保持打开。

当前代码只有 bot 导航、设置和 bot 内依赖当前对话的自动化弹窗，尚未实现下述全局管理页面；此前四页签示意只覆盖详情中的部分内容。

### 全局导航与 bot 内入口

保留当前 bot 图标列表作为工作区入口。在左侧固定区域增加“管理”，进入有文字导航的完整管理页面，包含：

```text
i-bot
├─ 我的 bot：进入各 bot 工作区，使用聊天、电脑、浏览器与成果
└─ 管理
   ├─ 任务：本人委托、自动化运行、外部请求及待处理事项
   ├─ 自动化：定时与事件规则
   ├─ 对外服务：所有 bot 已开放的业务服务与外部入口
   ├─ 我的连接：本人账号、业务连接与来源连接
   └─ 设置：模型、通知与默认额度
```

bot 顶部和设置中的“对外服务”跳到同一管理模块，并预先筛选当前 bot；全局入口展示本人全部 bot 的服务。两处引用相同服务与规则，不产生两套配置。返回工作区时回到对应 bot，不要求用户先建立或选择私人对话才能管理服务。

首期页面地址建议为 `/manage/services`、`/manage/services/{serviceId}`、`/manage/connections`、`/manage/tasks`、`/manage/automations`。这些是待开发页面位置，不是已经可访问的路径；账号及模型设置沿用并扩展现有设置。未使用对外能力的用户可以继续直接进入 bot 工作区。

平台内使用别人的服务与管理自己的服务应分开呈现：前者只显示本人获准使用的服务、输入与自身请求结果，后者配置能力、权限、连接和运行。前者为后续产品扩展，不代表当前已实现服务发现或共享访问。多人共用完整 bot 工作区、组织统一代管另需明确角色与授权，不作为独立平台账号的隐含权限。

### 服务、入口、连接与任务的关系

- 一项对外服务归一个所有者和一个 bot，例如“需求助手”；一个 bot 可以提供多项服务。
- 服务定义用途、开放能力、业务资源、所用连接、结果范围、权限与预算。
- 服务可以接飞书、webhook 等多个外部入口；每个入口有自己的来源认证、路由、输入映射和结果投递。入口可以进一步收紧服务范围，不能扩大服务授权。
- 来源连接和业务账号集中保管，具体服务保存受控引用。连接成功不自动对所有 bot 或外部人开放。来源服务的既有凭据由其维护者管理，不因关联而导入其他所有者账号。
- 每次外部请求产生单独的任务和上下文，绑定服务、入口、原请求身份、资源与结果目标；不复用私人聊天历史。管理任务页汇总状态，外部人只在原渠道收到获准结果。
- 来源已有权限规则必须继续生效；i-bot 的资源和能力范围不能放宽它。目录同步、身份缓存和连接引用均按所有者及实际获准应用/企业范围隔离。

### 对外服务列表与服务详情

列表显示名称、所属 bot、用途、接入渠道、运行状态、待处理事项与近期失败；新建服务先选择所属 bot。初次为空状态，提供“创建对外服务”和用途示例。

服务详情先展示是否可用、最近任务和需要本人处理的原因，再进入能力、权限、入口和记录配置。运行状态区分草稿、待联调、运行中、暂停、需要处理；连接状态单独展示。收到一条请求不能证明权限和结果投递均已成功。

服务中的外部入口列表用于查看具体渠道；不是整个产品的唯一管理入口。

### 入口列表

每行显示：名称、来源、开放能力、接入状态、启停、最近事件；操作有进入详情、暂停、重新接入、删除。接入状态区分草稿、等待来源配置、待联调、可启用、授权失效；“最近收到请求”不能代替“接入全部成功”。

示意结构：

```text
我的 bot / 外部入口                         添加入口

需求助手       飞书 · Triage    查询 / 创建需求    待联调
客户事件       Webhook         整理处理建议       已暂停
```

### 入口详情：四个页签

1. **开放能力**：动作、所需输入、固定业务资源、业务账号、交付内容。未安装插件/连接失效提示补齐；不可把通用 shell、整个个人浏览器勾为默认外部能力。
2. **调用权限**：人员/部门或服务列表 × 开放动作；明确允许/禁止及有效期，默认不允许未知身份。可选择某身份与资源查看规则判断，此操作不执行实际业务。
3. **接入**：来源方式、应用/来源标识、路由、地址与密钥配置、事件范围、测试步骤。实际缺项逐项显示，不模拟生成已生效凭据。
4. **记录**：接收者/来源、请求动作、资源、判断、任务状态、投递状态；展开看必要输入、规则来源、回执及失败原因。敏感字段脱敏。

面向用户的顶层页不展示签名实现细节。接入协议、代码示例、原始错误等放到“接入详情”，用于维护者排查。业务参数只有必要字段，如团队、标题、说明，不要求填 sandbox 路径或模型工具名。

## 3. 开放能力怎样定义

用 Triage 创建需求为例：

- 名称：创建需求；动作标识来自受支持能力注册，不靠自然语言猜写入类型。
- 输入：标题、需求说明、可选来源链接。团队固定为所有者选择的团队；外部输入不能改到其他团队。
- 业务连接：所选 Linear 连接及实际可用状态；外部请求只在指定范围使用。
- 工作：必要时补充需求信息、查重、创建、回读并保存结果。具体确认沿用已授权任务范围；授权规则不由 agent 修改。
- 输出：需求编号、摘要和允许交付的原平台链接；不回传个人聊天历史或连接密钥。

每个外部能力至少有动作、输入约束、工具与资源范围、连接引用、输出范围和执行策略。首期优先接已有可信业务工具；任意导入插件没有这些约束时显示“暂不支持对外开放”，而不是自动把全部工具暴露。

## 4. 所有者创建入口的步骤

1. **选择用途**：例如需求查询/创建、事件分析。也可以在本人聊天中描述，让 agent 保存配置草稿。
2. **选择来源**：Triage 等已有机器人、新的独立飞书应用、webhook。
3. **配置能力**：选择真实业务动作，设置资源、业务连接、输入和输出。
4. **配置外部权限**：从获准资料选 A/B，A 可查询/创建，B 仅查询；webhook按已验证服务身份配置。没有部门范围时先按人设置。
5. **接入与联调**：生成实际接入配置，由来源维护者完成转交；检查缺项，完成身份、权限和结果投递测试。
6. **启用**：所有者启用入口，记录当时配置版本。之后修改能力、人员、资源或停用，在下一次受控操作前按最新规则检查。

草稿、保存配置、生成密钥、真实联调和启用是不同状态。真实测试可能创建业务记录，必须让所有者看到测试动作、资源和发送目标；权限模拟不产生业务写入。

## 5. 已有 Triage 怎么接

首期优先“已运行的飞书机器人转交”。Triage 继续由现有服务接收飞书事件，i-bot 不用相同 App ID 再启动一个独立长连接。

### i-bot 所有者

选择 Triage 来源，配置入口及开放能力，得到接收地址、入口 ID、服务认证配置和转交示例。关联已有可信凭据服务时使用凭据引用，不要求复制 App Secret；服务密钥生成只显示一次，后续可轮换。

### Triage 服务维护者

配置转交到这个入口：验证飞书事件 → 匹配明确的业务路由 → 携带原请求人身份和事件信息 → 认证调用 i-bot → 将接收回执和后续允许的结果送回原会话。

必须验证应用/企业、来源事件和目标入口，不能接受正文伪造的 OpenID。转交的可信 sender 来自原始事件，而不是外部调用者自行填写。双方维护者不相同时，这一步需要 Triage 维护者配合；i-bot 界面保存成功不能代替来源服务已配置。

### 路由

一个入口绑定明确 bot/能力；同一应用关联多个入口时，使用明确的业务路由，例如目标会话与动作、已有 Triage 命令或服务选择。不能按“最后活跃 bot”猜归属。无唯一匹配时补充选择或返回可用业务提示，不执行任意个人 bot。

## 6. 新接飞书应用怎么接

所有者或应用开发者准备独立应用的 App ID/Secret、已生效机器人权限、消息及卡片订阅、可用范围，必要时配置 OAuth/回调。i-bot 保存凭据或引用，检查应用身份与配置，再设置可接收会话和业务路由。[飞书配置前提](../research/feishu-integration-prerequisites.md)

本地可按官方支持方式用长连接联调；正式环境要持续在线。固定 Web 链接和 HTTP 接收模式需要相应可访问域名。先检查该应用是否已有接收服务，不能默认多起连接。发送权限、卡片回复、来源权限和目录权限分别检查。

## 7. Webhook 怎么接

所有者选择来源系统，配置开放能力、字段映射、资源和服务身份。接入页提供地址、认证配置、Node/curl 示例、示例 JSON、测试状态和结果回调设置。

已有 HMAC 格式、事件 ID 去重、时间戳、队列及回调可复用；现有 route 不是已经支持本设计的能力/人级授权，新增入口需先接上这些约束。[现有 webhook 协议](../automations-and-webhooks.md)

签名密钥证明来源服务。按人规则仅适用于已配置可信身份来源且确实验证了人的转交；普通服务事件不根据 body.userId 自动提升为某个人的权限。输入只填可变业务字段，外部传入目标资源必须在已开放范围内。

接收先保存事件并返回接收状态，后台执行完成后再回调。队列、等待人工、业务失败和回调失败分别展示；补发回调不重执行业务。

## 8. 外部使用者的体验

同事在飞书 @Triage：“创建需求，内容是……” → 来源服务路由到入口 → i-bot 验证 A 权限并排队 → 飞书收到已接收及业务任务标识 → 必要字段通过原会话/卡片补充 → 创建成功返回编号和链接。

B 同样请求时，返回“当前不能通过这个入口创建需求，可以查询已获准需求”；不创建业务任务，不暴露权限管理页面或其他人的规则。

需要所有者登录业务账号或处理私人环境时，通知所有者到 i-bot 接管；外部人员仅收到“等待入口所有者处理”等允许摘要，不获得电脑入口。普通外部字段补充可在飞书完成，回复身份与当前任务绑定。

## 9. 需要怎样提供后台能力

| 部分         | 拟实现职责                                                                        |
| ------------ | --------------------------------------------------------------------------------- |
| 外部入口记录 | owner/bot、来源、能力、路由、状态和预算；由本人管理                               |
| 能力与规则   | 动作、输入、工具/资源、连接、人员/服务、规则版本与判断原因                        |
| 来源适配     | Triage 转交、独立飞书应用、普通 webhook，输出统一的可信外部请求上下文             |
| 执行         | 复用目标/任务及自动化调度基础，外部模式使用限定工具和上下文；不借整个个人电脑权限 |
| 回复与交付   | 来源回执、卡片补充、完成/失败通知、回调重试与数据范围                             |
| 联调和记录   | 配置检查、无写入权限模拟、真实测试、接收/执行/投递追踪                            |

共享 Zod 契约与 Drizzle 表统一定义；管理路由沿 owner 链检查，外部接收路由使用来源认证。实际 API 路径及 JSON 契约在实现阶段确定，不将本文或示意界面的占位地址当成可调用接口。

现有“自动化”负责定时/事件规则和运行；新“外部入口”负责业务能力、来源和外部权限。执行队列、去重、人工请求、结果投递尽量共用，避免另建互不关联的 agent 执行体系。

## 10. 当前基础与缺口

已有码：自动化弹窗、定时/签名 webhook、运行记录、队列与回调。当前 webhook 自动化使用 bot 的既有工具和对话，不具备本设计完整的外部能力/请求人约束。

待新增：全局管理导航、对外服务列表/详情及入口向导、连接和任务汇总、能力注册及外部执行支持、飞书适配和可信转交、按动作资源的外部规则、外部上下文隔离、模拟与真实联调、飞书结果交付。

第一版验证一个完整场景：所有者配置“需求助手”，Triage 转交 A 的创建请求成功，B 被拒绝；重复事件不重复创建，结果回到原获准会话；所有者可暂停入口，外部人员始终无个人平台访问权。

## 11. 管理、执行和对外使用怎样部署

管理页面由现有 i-bot Web 提供；本人通过平台登录管理服务、连接和任务。API 接收可信外部事件，完成身份、能力及资源检查，将任务持久化后执行和交付。飞书机器人、外部系统或后续业务网页是外部使用渠道，不提供私人管理页面访问权。

首期沿用一个持续在线的 API 实例与 Postgres，复用现有自动化队列并补齐外部执行约束。当前自动化调度随 API 进程运行，桌面控制和 SSE 仍有进程内状态；不能仅启动多个 worker 就声称已支持并行、多实例或无中断恢复。后续将执行拆为独立进程时，先完成任务领取、控制归属、事件传输与恢复检查。

使用 API 工具的业务不应要求为每个请求启动电脑；确需电脑时使用该 bot 的受控环境，遵守单控制者与本人接管规则。等待桌面或某项人工输入的请求必须可定位；不锁住整个管理系统或其他 bot。不同任务能否并行按实际资源和执行能力决定，不仅由界面状态决定。

sandbox 是按需执行和预览环境，不保存唯一的服务配置、权限、任务或账号连接。对外地址来自持续在线 API 或正式发布服务；sandbox 临时预览不能作为长期 webhook 接收地址。关闭前端不停止已委托任务，但运行 API 的机器必须在线。本地休眠或停止 API 时明确提示服务无法接收/执行，不承诺持续可用。

需要本人确认的任务，在任务页和通知中展示动作、资源、使用账号及结果投递目标。可阻塞当前请求，或暂停相关步骤让不依赖该答复的工作继续；能否继续须由任务依赖与资源检查决定。外部请求人补业务字段和所有者授权是不同操作。

服务暂停后停止新接收，未开始的请求暂停并允许本人处理；已经运行的请求独立展示可停止操作。恢复前重新检查身份、当前规则和已发生的外部动作。交付失败重试投递，无法确认是否已写入时先核查业务回执，不能默认重做。

独立企业后台仅在出现管理员代管、公司集中分发应用、统一审计或统一付费等真实需求后另行设计。它需要独立角色与数据权限，不能通过新增通讯录页面自动取得管理个人 bot 的权限。

验收应覆盖产品路径：从全局管理创建服务，或从 bot 跳到同一服务；选择已有连接并完成来源维护者配置；授权和拒绝分别联调；关闭管理页面后服务继续；失效与人工处理能通知本人；暂停和恢复可查记录；外部人始终只获得获准业务结果。
