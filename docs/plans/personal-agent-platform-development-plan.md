初稿日期：2026-09-30；更新日期：2026-10-13。本文是待开发计划，现有基础与缺口来自当前工作目录核查；外部配置要求来自官方文档。没有创建云资源、发布飞书应用或执行真实账号操作。

## 1. 已确认的范围

用户已确定：

- 飞书首期关联已有企业应用，提供本人账号连接、获准通讯录查询、机器人通知和外部业务请求；i-bot 平台及个人电脑只供各 bot 所有者本人使用。
- 已有 Cloudflare 账号，需要新建 R2 bucket。
- 先本地联调，已有域名后再配置正式登录回调和外部调用地址。

外部条件备注（2026-09-30，用户补充）：飞书管理员配置，以及飞书应用的组织架构/通讯录读取权限可能尚未具备，目前状态待确认。成员与部门同步仍在计划范围内，真实联调和验收需等待管理员确认权限已生效、通讯录数据范围已配置；不能视为这些条件已经满足。

范围补充（2026-10-13，用户要求）：加入 sandbox 保活与恢复改造；组织信息优先通过现有 Triage 机器人获准能力接入。当前没有公司管理员可配合，个人账号连接与登录状态管理先行，完整组织同步保留为后续条件满足后的能力，不阻塞个人 agent 使用。

同日需求澄清：产品重点是公司内每个人的 bot 能使用本人安全连接的账号持续执行任务、打开网页、预览/接管、发消息并保存成果。通讯录提供找人、确定收件人和负责人等辅助能力；首期取消默认“组织资料”页面，相关信息只在任务查询和人员选择中呈现。账号授权、任务执行、结果与恢复为默认入口。[具体设计](../research/personal-agent-feishu-work-execution-design.md)

最新边界澄清：i-bot 是供多位用户使用的平台，同事可以拥有自己的平台账号、bot、连接和服务；平台用户身份不自动授予其他所有者的 bot、私人会话或电脑访问权。对外开放的是关联飞书机器人/webhook中明确的业务能力；通讯录在该入口的后台配置中判断哪些请求人可触发哪些动作。新增“外部入口”管理；完整 bot 共享、团队/公共 bot 分类与组织代管作为另行定义的能力，不限制其他人独立使用平台。本人通用网站登录独立管理，已登录携程等网站可使用浏览器操作，不要求专用 API 插件。[外部入口设计](../research/bot-access-and-organization-design.md)、[插件与网站身份](../research/personal-account-plugin-and-browser-auth.md)

首期产品验收场景：用户通过 Web 或飞书发起任务，agent 在 sandbox 处理用户上传的材料，保存目标和执行进度；需要补充信息时能选择阻塞或非阻塞；完成后交付可下载文件，并通过飞书通知。关闭 Web 页面后执行继续，服务重启后状态可以恢复。

之后扩展 Gmail、内部业务平台、网页长期发布、外部任务 API、Web Push、多协议客户端，以及更多文件处理能力。

相关评审：[应用层能力](../research/personal-agent-application-capabilities.md)、[目标与执行能力](../research/personal-agent-harness-review.md)、[轻部署](../research/aiproxy-lite-deployment-review.md)、[飞书接入前提](../research/feishu-integration-prerequisites.md)、[个人飞书长期连接](../research/feishu-personal-account-connection.md)。

### 2.1 R2：创建与填写步骤

1. 在 Cloudflare 控制台启用 R2，创建测试 bucket，例如 `ibot-artifacts-dev`；保留私有访问。正式环境再建立单独 bucket 和凭据。[创建说明](https://developers.cloudflare.com/r2/buckets/create-buckets/)
2. 在 R2 的 Manage API Tokens 创建凭据，选 **Object Read & Write**，限定到该 bucket。复制返回的 Access Key ID、Secret Access Key 和 S3 endpoint；Secret 只展示一次。应用读写对象不需要 Cloudflare 全局 API Key。[凭据说明](https://developers.cloudflare.com/r2/api/tokens/)
3. 配置现有四个字段：

```dotenv
R2_ENDPOINT=<控制台给出的 S3 endpoint>
R2_ACCESS_KEY_ID=<Access Key ID>
R2_SECRET_ACCESS_KEY=<Secret Access Key>
R2_BUCKET=ibot-artifacts-dev
```

endpoint 通常是 `https://<account-id>.r2.cloudflarestorage.com`；如果 bucket 采用特定 jurisdiction，使用控制台给出的地址，不自行拼接。

4. 为浏览器直传/读取配置 CORS，AllowedOrigins 填实际 Web origin。本地若同时使用 3000 和 3001，可分别登记；正式域名确定后再加入。下面是首期 PUT/GET 的控制台配置示例，不代表配置已经应用：

```json
[
  {
    "AllowedOrigins": ["http://localhost:3000", "http://localhost:3001"],
    "AllowedMethods": ["GET", "PUT", "HEAD"],
    "AllowedHeaders": ["Content-Type"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3600
  }
]
```

后续请求若发送额外校验头，需要按实际请求补充 AllowedHeaders。服务端 S3 调用不依赖浏览器 CORS；浏览器使用签名 URL 仍需要 CORS。[CORS 说明](https://developers.cloudflare.com/r2/buckets/cors/)

下载采用私有对象的短期签名链接，首期不需要公开 bucket、自定义文件域名或 Cloudflare Workers。签名 URL 过期后重新鉴权生成；对象的保留和删除由平台管理。

### 2.2 飞书：SDK 与应用配置

服务端计划使用官方 Node SDK `@larksuiteoapi/node-sdk`。安装 SDK 由开发完成；企业权限来自自建应用配置、发布和管理员授权，SDK 本身不能读取未经授权的组织信息。[官方 SDK](https://github.com/larksuite/node-sdk)

用户准备 App ID 和 App Secret 后，开发时增加环境变量解析、连接检查和脱敏状态。以下名称是本计划拟新增字段，当前应用还不识别它们：

```dotenv
FEISHU_APP_ID=<企业自建应用 App ID>
FEISHU_APP_SECRET=<企业自建应用 App Secret>
```

首期选用官方 SDK 长连接接收 `im.message.receive_v1` 消息事件和新版 `card.action.trigger` 卡片回调；旧 `card.action.trigger_v1` 不支持长连接。事件订阅与回调订阅要分别配置。需要 HTTP 接收时，再准备后台的 Verification Token、Encrypt Key 与公网回调地址。本地长连接不替代用户登录重定向配置。[事件长连接](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/event-subscription-guide/long-connection-mode)、[回调接收方式](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/event-subscription-guide/callback-subscription/configure-callback-request-address)

应用配置应逐项区分：

| 能力             | 准备事项                                                               | 产品行为                                          |
| ---------------- | ---------------------------------------------------------------------- | ------------------------------------------------- |
| 飞书登录         | 准确登记的重定向地址、用户身份授权；纯身份确认不要求额外业务 API scope | 关联已有 i-bot 账号或建立新账号，不按姓名猜测账号 |
| 成员/部门同步    | 接口所需通讯录只读权限、获批通讯录数据范围                             | 只同步获准部门与成员；不申请管理或修改通讯录      |
| 机器人通知       | 机器人能力、以机器人发送消息权限、测试成员可使用应用                   | 目标完成、失败、需要人处理时通知                  |
| 任务发起/回复    | 接收机器人单聊和群聊 @ 消息的权限与事件订阅                            | 事件去重后建立任务，回复对应原任务                |
| 卡片中的人工回复 | 卡片回调支持和回调处理器                                               | 校验回复人及请求版本，再保存输入或审批            |
| 正式试点         | 版本发布、企业审批、应用可用范围、固定部署地址                         | 公司管理员可看接入状态与失败原因                  |

机器人首期申请 `im:message:send_as_bot`、`im:message.p2p_msg:readonly`、`im:message.group_at_msg:readonly`。通讯录采用经管理员批准的只读字段权限组合，包含授权范围、部门、员工基本信息、部门关系和成员状态；精确列表见 [飞书接入前提](../research/feishu-integration-prerequisites.md)。部门试点从获准部门查询，不从需要全员权限的根部门 `0` 开始。不要为了方便一次申请读取所有群消息、修改通讯录或全部云文档。

`tenant_access_token` 用于企业应用身份；`user_access_token` 用于用户委托身份。i-bot 自身 session 与这两类 token 分开管理。纯登录不要求 `offline_access`；需要后台代用户调用 API 时才增加该授权，并实现过期判断和 refresh token 轮换。新接入按当前 OAuth v3 文档使用 `https://accounts.feishu.cn/oauth/v3/token`，不直接复制历史 v2 示例。不能把管理员开通应用视为所有成员已经授权。[用户令牌](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/get-user-access-token-v3)、[刷新令牌](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/refresh-user-access-token-v3)

公司管理员还需确定：哪几个部门可同步、谁能配置公司连接、哪些 bot 可以使用连接、哪些业务写入需确认。飞书应用可用范围、通讯录数据范围、i-bot 角色和具体业务数据权限分别保存。

### 2.3 本地联调与以后需要的配置

| 能力                          | 本地可做                                                    | 何时需要外部配置                                                                  |
| ----------------------------- | ----------------------------------------------------------- | --------------------------------------------------------------------------------- |
| 目标、会话、人工请求、文件 UI | 使用现有 Postgres 和 sandbox 开发                           | 长期后台运行需要持续在线的 API/worker 与持久数据库                                |
| R2 上传与下载                 | 有上述测试 bucket 即可                                      | 不需要先准备正式域名                                                              |
| 飞书事件                      | 优先验证官方 SDK 长连接                                     | HTTP 回调需公网 HTTPS；本地机器休眠时无法保持处理                                 |
| 飞书登录                      | 先确认后台能登记的开发回调；实现 state、code 交换和账号关联 | 若后台不接受本地地址，联调使用临时 HTTPS 地址；正式回调待域名确定                 |
| 飞书任务卡片                  | 验证消息收发与回调；页面入口先在本机检查                    | 卡片里的 localhost 页面只适合同机调试；公司试点需要可访问的正式 Web 地址          |
| Gmail                         | 可先开发连接管理与适配器                                    | 真实授权需要 Google Cloud 项目、OAuth Web Client ID/Secret、同意屏幕和测试账号    |
| Gmail 新邮件触发              | 先手动执行邮件流程                                          | 启用 Gmail API、Cloud Pub/Sub topic/subscription 与相应权限后接入 watch；定期续订 |
| Web Push                      | 先有站内通知                                                | 后续开发生成 VAPID 密钥，并配置浏览器订阅与通知权限；正式站点需合适的 HTTPS 环境  |
| 邮件通知                      | 先用飞书通知                                                | 选定邮件发送服务后提供 SMTP 或供应商 API 凭据、发信域名配置                       |
| 网页长期发布                  | 先保留 sandbox 预览与源码下载                               | 确认现有 AIProxy Key 的轻部署权限、配额、接口契约及访问控制                       |
| 内部平台连接                  | 先完成统一连接模型                                          | 每个平台提供测试环境、API 文档、授权方式、数据范围和可执行动作                    |

Gmail 后续按需申请 scope；只读邮件和草稿等 scope 可能涉及受限权限及审核，不能把安装插件等同于完成授权。新邮件通知还需要 Cloud Pub/Sub，不能只配置一个自定义 webhook URL。[Google OAuth](https://developers.google.com/identity/protocols/oauth2/web-server)、[Gmail 权限](https://developers.google.com/workspace/gmail/api/auth/scopes)、[Gmail 通知](https://developers.google.com/workspace/gmail/api/guides/push)

Web Push 接入包括 Service Worker、订阅和用户许可，服务器通知记录本身不能证明浏览器已收到推送。[Push API 规范](https://www.w3.org/TR/push-api/)

当前不要求先准备 Redis、R2 公网域名、Gmail、移动端推送或额外轻部署上游 Key。第一版持久执行复用 Postgres 状态与租约；扩展多实例时再根据吞吐和通知需求确定共享事件传输。

## 3. 技术与数据约定

### 3.1 先处理架构说明与实现的差异

仓库 AGENTS.md 锁定 Mastra、Vercel AI SDK、NestJS、assistant-ui；当前运行代码使用 Hono、直接 AI SDK 和自有聊天组件。开发按仓库锁定的技术体系规划；阶段 0 记录差异及向约定体系迁移的步骤，把 HTTP 接入、执行器和 UI 分别处理，并保护已实现功能。不能把尚未接入的 Mastra memory 或 suspend/resume 当成已有能力，也不另引入一套执行框架。

业务状态由 Drizzle 管理，执行器和 UI 协议通过接口读写这些状态；迁移时已有自动化、登录续期、预览和插件功能应有回归验证。框架不能自行建表或保存第二套权威执行状态。

### 3.2 需要增加或扩展的记录

| 记录             | 主要内容                                             | 与现有数据的关系                                            |
| ---------------- | ---------------------------------------------------- | ----------------------------------------------------------- |
| 目标             | 完整要求、验收条件、预算、状态、剩余工作、成果       | 用户明确委托或自动化触发时创建；普通咨询可不创建            |
| 执行与检查点     | 目标/会话、结束原因、租约、可继续位置、动作回执      | 扩展现有 agent jobs 和 automation runs，统一调用执行器      |
| 子会话与分支关系 | 父会话、分支起点、上下文引用、子任务依赖、合并记录   | 复用 conversation/message，子任务内部消息独立保存           |
| 人工请求         | 阻塞方式、影响范围、内容版本、接收人、回复、截止时间 | 桌面接管、表单输入、审批均关联目标/任务                     |
| 文件与成果       | owner、bot、目标、原件/副本、对象引用、版本、来源    | 扩展 attachments 关联；同一文件只有一份权威元数据与对象引用 |
| 连接             | 外部账号/企业、权限、加密 token、有效状态、bot 授权  | 复用 vault，插件只引用 connectionId                         |
| 外部人员与规则   | 来源企业/应用、外部人员与部门、规则版本和状态        | 服务于外部入口鉴权，不建立共享平台成员                      |
| 通知及投递       | 事件、收件人、未读、通道、重试、投递结果             | 统一现有自动化未读与新增任务通知                            |
| 网站/服务与发布  | bot、项目、版本、预览、部署 ID、endpoint、访问范围   | 将 sandbox 内项目配置关联到持久记录                         |
| 记忆             | 事实/偏好、来源、适用范围、修改记录                  | 与技能库分开表达，用同一 DB 权限纪律检索                    |

表名和精确字段在阶段 0 确定。所有共享 Zod 契约放 `packages/types`，所有表和迁移放 `packages/db`；二进制存 R2。消息继续使用唯一 `messages.parts`，AG-UI 或应用卡片在边界适配。

每个 bot 的平台、私人会话、文件、账号与电脑仅向其所有者开放。外部入口只触发明确的业务能力和受控结果，不给外部人员平台访问权。仍遵守一个 bot 对应一个活动 sandbox、一个桌面控制者。

新增记录包括外部入口绑定、可信来源和外部请求人、业务动作与资源规则、业务连接、规则版本与变更记录。外部人员不建成个人 bot 的共享平台成员。已有 Triage 权限作为外部权威约束时通过适配器读取/编辑，不复制同义 ACL 后并行维护。创建、修改和研发执行需可区分的动作；具体表和契约在阶段 0 定义。

### 3.3 Triage 组织信息与个人飞书连接

Triage 作为组织信息来源，个人飞书连接作为个人账号身份，两者分别管理。

- 接入前验证 Triage 当前的已知成员查询、人员搜索、部门列表、部门成员接口；分别记录身份、字段、权限和数据范围。不能把某个查询成功写成全公司通讯录可用。
- 任务需要查询组织结构时，优先按部门树组织：接口允许时先读取已授权部门范围，从获准部门分页读取子部门，再按需读取直属成员；部门选择器和明确的组织查询可展开部门，人员搜索作为补充。成员可能属于多个部门，身份去重与部门关系分别保存。普通任务不要求先读取完整目录。
- 优先使用 Triage 已批准能力，通过受控接口转发必要查询；i-bot 校验请求人的公司、角色和可见范围，Triage 不提供任意 OpenAPI 代理，不将应用 Secret 发给个人 agent。
- 已知成员、允许的部门和用户提供的组织资料可作为部分资料，保存来源、读取时间与完整性。未知部门/主管字段显示“未知”；逐人查询不能证明目录完整。
- 人员身份保留应用和企业范围。Triage 的 open_id 不直接用于另一飞书应用；有官方映射证据时再关联，不按姓名自动合并。
- 无法读取的完整组织架构保留待配置状态；组织资料不能自行授予共享 bot、连接或业务写入权限。

2026-10-13 用户说明 Triage 可以查询通讯录，因此部门树作为需要组织结构时的优先查询方式；默认不提供独立组织资料页。此前根部门 `0` 的权限失败不能推断所有具体部门都不可读；如果不具备根部门全员范围，从获准部门开始，显示“当前可见范围”。部门树提供层级，人员列表仍需成员接口；领导关系在字段有权限且实际返回时展示，不从部门层级猜测。[子部门接口](https://open.feishu.cn/document/server-docs/contact-v3/department/children)、[授权范围接口](https://open.feishu.cn/document/server-docs/contact-v3/scope/list)

另一条可评估的组织查询方式是本人明确授权的用户 OAuth。飞书官方说明：用户身份调用通讯录 API 受本人组织架构可见范围约束，而非应用身份的通讯录数据范围；仍需应用已开通对应用户身份 API 权限并获得用户授权。因此可在既有应用权限满足时查询本人可见组织，无需先为机器人申请全员范围；这不会改变 Triage 机器人权限，也不能读取本人不可见成员。[通讯录权限范围](https://open.feishu.cn/document/ukTMukTMukTM/uETNz4SM1MjLxUzM/v3/guides/scope_authority)

个人账号连接作为个人 agent 的基础能力，首期支持两种方式：

| 方式               | 使用体验                                           | 持久与恢复                                                                                            | 前提                                                              |
| ------------------ | -------------------------------------------------- | ----------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- |
| 飞书官方用户 OAuth | 本人授权后，在允许的 scope 内后台读写 API          | 加密保存 access/refresh token、有效期和授权范围；自动刷新、失效通知与重新连接                         | 应用已有所需用户身份权限及回调配置；持续调用需 offline_access     |
| 飞书网站浏览器登录 | 本人在 bot 浏览器扫码/登录，agent 接着使用获准页面 | sandbox 内保留网站状态；本人选择“保存登录状态”后加密保存可恢复的网站状态，换 sandbox 后尝试恢复并检查 | 不依赖新建飞书 API 应用，但受网站登录、设备验证和实际页面能力限制 |

纯飞书登录只用于建立 i-bot 会话，不代表已获得后台业务 API 授权。官方 OAuth 的 refresh token 会轮换，授权过期、撤销或权限变化时需本人重新连接；浏览器状态也可能被网站或设备校验拒绝。产品承诺自动续期、检查和恢复，不承诺永久免登录。

刷新任务不依赖聊天正在运行；同一账号串行刷新并原子保存新令牌与有效期，避免两个 bot 同时使用只能用一次的 refresh token。定期检查授权到期时间，失效时只阻塞依赖该账号的工作。具体有效期按响应处理，不把示例值写成常量；官方当前说明用户授权达到 365 天需要重新授权。[个人连接资料](../research/feishu-personal-account-connection.md)

“我的连接”展示账号、连接方式、作用 bot、权限、检查时间与“正常/需要登录/等待验证/已断开”。任务遇到登录失效时建立影响对应步骤的人工请求，保存进度；其他独立工作可继续。登录完成后从实际业务状态继续，不重复提交已完成操作。

凭据与网站状态由服务器受控解析，不进入记忆、普通附件、成果包或模型文本。需要持久化的网站状态使用独立加密存储：结构化记录由 vault 管理，较大二进制快照放私有 R2 并单独鉴权。恢复限制到明确授权的账号与 bot；保存、恢复、删除可审计，用户可断开连接并删除所保存状态。浏览器恢复只支持经过验证的格式与版本，不宣称复制 profile 就能恢复所有网站登录。

官方飞书 CLI 可以作为已有应用的接入方式：本人明确完成用户授权后，使用独立用户配置执行支持的 API；实际刷新能力需按安装版本验证。多租户不能共用本机默认 CLI 用户授权，也不自动复制现有 Triage 配置。CLI 仍受公司应用管控；官方个人远程 MCP 的新服务当前只有 7 天有效期，不作为长期连接的默认方式。具体来源和条件见 [个人连接资料](../research/feishu-personal-account-connection.md)。

### 3.4 个人 bot 的操作身份与长期任务

每个 i-bot bot 保存自己的 owner、会话、目标、账号授权绑定与成果。平台账号记录及后台执行独立于 sandbox 生命周期；首期可共用 Triage 的飞书应用机器人，通过可信发送者路由到各自 bot，不要求每人另建一个飞书应用。

每次外部操作明确使用机器人 API 身份、本人 OAuth 身份或对应网站浏览器会话。普通消息创建/回复支持本人令牌和相应 `im:message`、`im:message.send_as_user` 权限，但收件人、群聊、类型和回复限制分别验收。机器人 token 不替代个人 token，个人 API 授权也不直接成为其他网站的登录 Cookie。[消息身份核实](../research/feishu-message-identity.md)

服务端凭据工具先校验 owner、bot 和实际授权，模型仅引用连接名称，不获得 token。账号关联根据验证过的授权回调与官方用户身份，Triage 事件参数和姓名不能自报身份。多人、多 bot 账号隔离，用户能停止任务、撤销授权和删除保存状态。

网页登录保存还须处理当前 root shell 能读取 sandbox 内 Chrome profile 的边界：设计服务器维护的隔离浏览器执行环境，把敏感登录状态与通用命令/代码执行分开，按 bot/账号提供受控操作和本人接管。加密备份不等于工作中的秘密无法读取。所需持续在线浏览器服务与加密存储在实现前列入部署配置；使用原 sandbox 浏览器时明确其授权和隔离程度。

在线问卷、报告整理、持续跟进等使用同一流程：保存目标及所选账号 → 后台执行 → 实际浏览器画面/文件预览 → 必要人工请求 → 验证提交或发送结果 → 保存回执和成果 → 通知。恢复时核查原页面和外部动作是否已完成，不能重复提交。[流程与验收](../research/personal-agent-feishu-work-execution-design.md)

### 3.5 外部入口的权限与组织关系

每位平台用户管理自己拥有的 bot、连接与服务；其他人可以独立使用平台。服务调用权与 bot 工作区访问权分开，当前私人工作区沿所有权保护；未来协作须另定义明确授权。启用对外服务后，所有者在全局“管理 → 对外服务”配置所属 bot、开放能力、目标资源、业务连接、飞书或 webhook 入口，以及外部人员/部门或服务身份的允许/禁止规则。bot 内保留跳转到同一管理页面的快捷入口。

Triage 例子：A 可经飞书创建指定 Linear 团队需求，B 只可查询；这两项授权均不允许访问服务所有者的 bot 工作区、历史或电脑。两人也可以拥有自己的平台账号。外部方通过飞书卡片或回调接收获准结果；无需成为本平台用户。规则由所有者管理，通讯录只帮助选择外部授权对象。

产品采用 i-bot 内的独立管理模块，共用本人账号；连接集中管理，服务指定受控引用，任务汇总本人委托、自动化和外部请求。每项服务属于一个 bot，可接多个外部入口；“开放能力、调用权限、接入、记录”是详情的一部分。所有者按用途、来源、能力、权限、联调、启用完成接入；已有 Triage 由其现有服务认证转交，独立飞书应用与 webhook 分别配置来源。接入保存、真实测试和启用分别展示，不将草稿显示为已接入。长期运行由持续在线 API/执行服务负责，独立部署执行进程须先解决当前进程内状态；不以 sandbox 临时链接承担长期入口。[整体产品结构与接入流程](./external-entry-product-design.md)

飞书身份从验证事件取得；webhook 的服务签名不直接证明请求体里的个人身份。按人授权的 webhook 来源还须提供可信原始身份；否则只按已配置的服务身份执行。工具实际执行前检查外部来源/身份、动作、实际资源、业务连接和当前规则；恢复与子任务不能切换为所有者权限。

保留所有 owner 路由保护；新增受控的外部任务入口。外部任务不注入私人历史，不开放通用 shell 或个人浏览器，只使用明确登记的业务能力；任务在群里发起不自动批准公开敏感成果。默认不开放未知受控动作，已有 Triage 权限源保持单一来源。[具体规则与验收](../research/bot-access-and-organization-design.md)

### 3.6 应用插件与通用网站身份

一个 Google 或飞书插件可包含多项工具和流程，账号连接按需要获得真实 API scope；安装插件不等于全产品已授权。Google 的邮件/文件/日历等按任务增量授权，飞书遵守其应用及用户权限；工具尚未实现或上游未授权时明确显示原因。

本人网站操作使用独立通用浏览器能力。用户可在 bot 浏览器输入密码、扫码或完成网站验证，登录后沿用认可的会话进行页面操作。不存在专用 API 插件、没有 API scope、没有外部调用人员许可，都不能作为拒绝本人已登录网页操作的理由。API 调用不具备条件时可使用页面实际支持的方式，不伪造接口权限。

身份保存分为 API token、网站会话和可选的登录凭据。API token 由服务端刷新；浏览器保存网站所需的 cookies/存储或独立 profile，恢复后检查；用户名密码只有本人选择保存时进入加密凭据管理，并限定账号与登录域名，通过受控填充使用，不要求在聊天里粘贴。短信码、设备验证、硬件认证等需要时仍由本人完成，不把已保存状态当成永久有效。

“我的连接”展示 API 授权与网站登录的各自状态：未连接、已授权/已登录、需要补充授权、需要重新登录、等待验证。API 未授权不能覆盖浏览器的“已登录”；网站明确的访问拒绝或登录失效要与缺少插件分别展示。本人账号不自动开放给任何外部入口。[官方规则与恢复边界](../research/personal-account-plugin-and-browser-auth.md)

## 4. 分阶段交付

顺序：阶段 0 → 1 → 2 → 3 → 4；阶段 5 依赖 1、2 及轻部署契约；阶段 6 在状态与权限稳定后扩展。R2 与飞书应用准备可在阶段 0、1 开发期间进行，尚未有凭据时可做模拟适配，但不能标记真实集成验收通过。

### 阶段 0：状态与接口设计、架构接入

交付：

- 架构差异记录与接入步骤；锁定执行入口、持久状态和客户端协议边界。
- 目标/执行/人工请求/成果/连接/组织的契约、权限矩阵与数据库迁移计划。
- 区分本人任务与外部请求、入口来源和执行账号；定义外部入口的受控动作/资源规则，Triage 权限源适配保持单一来源。
- 配置示例与脱敏的连接状态检查；将新增配置声明到运行时 schema 和 Turborepo 环境变量。
- 明确租约、失败恢复、预算以及外部操作“已执行/未执行/无法确定”的处理方式。

代码范围：`packages/types`、`packages/db`、`packages/auth`、`apps/api/src/env.ts`、`context.ts`、执行入口与客户端接入文档。改动 packages 时添加 changeset。

验收：架构与状态只有一个归属；现有自动化、鉴权续期、插件与桌面/网页预览回归范围明确；不同用户与公司不能通过猜 ID 读写资源。

### 阶段 1：目标持续执行、会话、人工参与、sandbox 保活

交付：

- 目标的进行中、等待、暂停、取消、完成、失败、达到预算状态；状态页面展示完成证据与剩余工作。
- 单次模型执行结束后，根据验收结果及预算决定继续，24/48 步停止不能直接等同目标完成。
- 后台租约、检查点和恢复；前端关闭不终止已委托的后台目标；取消当前输入与取消整个目标分开。
- 子任务独立会话、父子依赖、fork 与结果合并；上下文摘要保留目标要求，数据库原消息不丢失。
- 人工请求同时支持阻塞与非阻塞，可影响一个步骤、任务或整个目标。等待某任务时，其他独立任务继续。
- 回复校验任务、接收人、版本与请求状态；迟到/重复回复不重复执行；超时按已定义规则处理，不当作批准。
- 人接管桌面期间 agent 不派发桌面点击；可继续独立的数据处理任务。
- sandbox 保活与恢复改造，见下节；目标与 sandbox 状态分别展示，机器关联不能代替实际续期结果。

代码范围：`apps/api/src/agent/{run,jobs,history,tools}.ts`、`automations/manager.ts`、`routes/chat.ts`、`sandbox/manager.ts`、`packages/core/src/sandbox/{keepalive,ppio-provider,handle}.ts`、共享契约/数据库、Web 任务与请求组件。

验收：步数停止后有预算就继续；阻塞任务 A 时独立任务 B 完成；非阻塞提问不暂停独立工作；重启后恢复只读工作，对状态不确定的写入核查或等待人处理；重复确认不造成第二次业务写入。

#### sandbox 保活与恢复改造要求

当前源码已确认两个缺口：`keepalive.ts` 续期失败主要记录日志；`ppio-provider.ts` 的重连异常分支会调用 `safeKill(instance)`，临时网络或桌面准备失败也可能导致删除既有实例。2026-10-10 查询到的存活状态只是当时的实例状态，不作为长期可靠性证明。

开发要求：

1. 保活由持续在线的 API/worker 负责，与长任务及桌面控制锁分开。配置保活策略和资源预算；电脑休眠/服务停止时明确显示不能保证续期，不能依赖网页保持打开。
2. 保存最近成功续期时间、控制面 endAt、已验证剩余时间、连续失败次数和重试状态；每次续期后读回到期时间。返回成功但窗口不足或没有有效延长时进入异常处理。
3. 续期请求具有可取消的超时，避免一个挂起请求永久阻塞后续保活；失败后在剩余时间内有界重试。按实际获准窗口安排间隔，临近到期时加快检查，避免固定间隔大于剩余时间。
4. 到期风险在桌面状态和通知中显示；恢复成功更新状态并合并重复提示。通知投递失败不阻塞保活，也不无限重建付费实例。
5. API 重启自动恢复保活；第一次恢复失败后继续调度重试，不能只等待用户下一次发消息。多 worker 对同一实例有归属和租约，避免重复恢复与启动服务。
6. 连接既有实例失败时，保留实例与归属，区分临时错误、需人工处理和控制面确认不存在。不能仅凭预览端口 404/502 就认定实例已被回收；不在重连失败分支默认 kill。
7. 新建实例准备失败的清理与既有实例连接失败分开处理。确认实例丢失后依授权恢复工作环境；新实例明确展示原临时文件可能丢失，已保存成果从 R2 获取，不静默当成原环境。

验收：模拟短窗口与续期静默失败、网络错误、请求挂起、API 重启及首次恢复失败；有风险提示且自动恢复不依赖前端轮询。临时重连/桌面准备失败不调用 kill；不存在实例的处理不破坏其他 bot，恢复不重复外部业务写入。长时间真实运行观察续期记录，短时查询不代替该验收。

### 阶段 2：文件、工作目录、成果与下载

交付：

- 通用上传、签名上传完成校验、文件登记和 sandbox 输入准备；不再只提供图片/视频 data URL。
- 工作目录约定：网页 `/root/projects/<projectId>`，任务临时工作 `/root/tasks/<jobId>`，待交付成果 `/root/outputs/<goalId>`。网页项目的 `design.md` 留在项目里。
- 文件面板、文本/代码编辑、图片/PDF/CSV 预览；原件保留，修改生成工作副本与版本；不支持预览的格式仍可下载。
- 用户交付成果上传 R2，提供鉴权下载；在线 sandbox 临时文件可走有大小限制的直接下载。
- 源码打包、文件名/MIME/大小、内容校验、过期链接重取、删除与保留规则；导出排除秘密文件和浏览器 profile。
- 大文件采用流式或分段方式；不无限制使用一次性 `readBytes` 加载内存。缺少 R2 时明确显示不能持久保存。

代码范围：`packages/storage`、`packages/core/src/sandbox/handle.ts`、`packages/types`、`packages/db`，新增 API 文件/成果路由，`ChatPanel` 与工作区文件 UI。

外部依赖：R2 四字段及 CORS。验收：上传材料进入正确任务；编辑不覆盖原件；跨用户访问失败；sandbox 回收后已持久保存的成果仍可下载；链接过期重新生成，不要求重做任务。

### 阶段 3：本人账号连接、网站登录与外部入口配置

交付：

- 官方 SDK 接入，应用凭据检查、企业应用 token 管理；必要用户委托授权及 refresh token 轮换。
- 飞书登录与现有身份系统关联，防止错误账号自动合并；登录续期失败后保留目标与返回位置。
- 读取获准的外部人员/部门资料，供入口权限配置使用；资料同步不自动创建平台账号或授予 bot 访问权。同事独立使用平台的账号接入按平台登录流程处理。
- 连接页面显示本人账号、API/网站登录各自状态、作用 bot、过期与撤销；外部入口使用的业务连接另行明确绑定。
- 外部人员状态/部门变更后重新检查入口规则；本人账号连接失效单独处理，不把外部人员列表当平台成员管理。
- 所有者的外部入口页面提供绑定、规则、事件记录和额度；通讯录不直接等同业务操作权限。
- 优先接 Triage 的获准组织查询，支持部分目录和来源说明；没有公司管理员时允许先使用个人账号，不将完整通讯录作为必填条件。
- 个人账号长期连接：OAuth 自动刷新/轮换、重新授权入口；浏览器本人登录、可选加密保存和跨 sandbox 恢复检查。先提供飞书的完整连接状态与人工恢复流程，再复用到其他网站。
- 区分机器人发消息、本人 API 发消息及网页登录操作；在任务/确认卡片中显示所用账号和身份。持久网页登录前完成受控浏览器与通用 root 命令的隔离设计及验证。
- 对外服务启用后才展示“外部调用权限”：指定外部人员/服务、业务动作/资源，支持有效规则检查和审计；不提供平台 bot 分享。

代码范围：`packages/auth`、`packages/db`、`packages/types`、`apps/api/src/secrets/vault.ts`，新增连接/组织/飞书适配模块及管理页面。

外部依赖：App ID/Secret、公司管理员审批、权限/数据范围与可用范围、开发回调和测试成员。验收：只同步获批范围；账号对应正确用户与公司；token 到期正常刷新；撤销后停止调用；公司 A 的资源不能被公司 B 或未授权个人读取。

当前前提状态（2026-10-13）：暂没有公司管理员。通过 Triage 接入已获准范围前，需维护者确认接入方式并核实实际权限；完整组织同步仍待条件满足。个人浏览器登录与连接管理可以先做；OAuth、机器人消息等依现有应用已生效权限分别验收，权限不足不自动切换身份。

### 阶段 4：飞书任务、通知、应用插件与自动化

交付：

- 单聊或群 @ 发起任务，记录经验证的外部请求人并路由到已配置服务及目标 bot；只有获准业务可执行，外部人不获得 i-bot 平台身份。
- 事件确认、验签/SDK 校验、去重和后台处理；HTTP 与长连接使用同一业务入口。处理失败可定位事件和任务。
- 如果复用 Triage 应用，事件继续由其现有服务统一接收，通过明确路由把获准的 i-bot 请求转交；不默认启动第二个独立长连接去争用同一应用事件。若使用独立 i-bot 应用，再单独配置订阅和接收。
- 任务结果、人工输入/审批卡片；原请求及卡片版本绑定，更新卡片不改变授权内容。
- 站内通知与飞书投递记录，通知偏好、安静时段、合并与重试；发送失败不重做业务任务。
- sandbox 到期风险、个人账号授权失效及等待设备验证进入通知和人工请求，并关联受影响任务。
- 飞书作为应用连接插件：安装、连接账号、给 bot 启用分别展示；依赖安装检查、版本、进度、日志及失败恢复。
- 定时报告、异常监测和平台事件复用现有自动化；先筛选/去重，再建立目标；用户可暂停、关闭或修改触发条件。
- 管理页记录关键业务操作与调用额度；业务动作是否确认依据已授权范围及具体内容，不能由邮件或网页中的文本授予权限。
- 外部业务调用在工具/API/MCP 接入和实际写入前强制授权；来源/请求身份、资源、规则和业务连接同时校验。本人任务不套用外部人员白名单；外部恢复不替换为所有者权限。

代码范围：`apps/api/src/automations`、`events/bus.ts`、`plugins`、飞书适配模块和新增通知服务，`AutomationPanel`、插件/连接/通知页面。

验收：重复事件只创建一次任务；卡片回复进入正确请求；关闭 Web 后仍收到重要通知；重复投递不重复执行；应用被停用时停止新事件处理；本地联调成功后在固定在线环境再次验收。

权限验收：A/B 经同一个 Triage 入口请求时 A 能创建、B 不能；两人都不能访问所有者的 i-bot 平台或电脑。伪造 webhook 个人身份、换工具、撤销权限和后台恢复不绕过规则。所有者正常操作已登录网站不因缺少 API 插件/外部白名单而失败。仅提示词检查通过不能标记完成。

阶段 1—4 构成首期交付，必须跑通“任务 → 人工请求 → 文件成果 → 飞书通知”的完整场景。

### 阶段 5：长期发布、外部调用与内部平台

交付：

- 网页/服务登记、项目与版本选择、预览/发布状态、源码成果；已有网页工作流继续自动设置路径、技术栈、端口。
- AIProxy 轻部署适配器，发布目录准备、部署状态、构建错误、endpoint 回读及健康检查；访问范围按部署方实际支持配置。
- 明确保存发布要求的基础 sandbox ID，不能使用 i-bot 行 ID 或 SDK 复合 ID；不因发布而删除 bot 的活动 sandbox。
- 外部业务 API：只触发已开放能力，查询/回复/交付相应受控任务；使用限定来源/bot/动作/资源的可撤销凭据及幂等键，不开放个人 bot 的通用聊天或电脑。
- 既有签名 webhook 与任务完成回调继续复用；发布生成网页、调用生成服务和调用 agent 任务 API 分别展示。
- 内部平台接入先选择一个真实业务系统：工单或报告查询、引用来源、明确授权后写回并保存回执。
- Gmail 后续插件：读取邮件/附件、应用内回复草稿、确认后发送；新邮件触发单独接 Pub/Sub/watch，不把草稿生成当成已发信。

外部依赖：轻部署权限及完整契约、固定可访问地址；内部平台测试 API；Gmail OAuth 与后续 Pub/Sub 配置。

验收：选定项目和版本正确；开发 sandbox 停止后发布链接仍符合服务保留策略；发布失败不显示成功；未授权 API 调用失败；重试不重复发信或创建工单。

### 阶段 6：记忆、登录状态、更多处理与多端交互

交付：

- 可查看、编辑、删除的个人事实/偏好及项目记忆，记录来源与适用范围；MVP 用 Postgres 检索，不引入 pgvector 依赖。
- 在阶段 3 的通用网页登录基础上扩展更多应用 API 和网站恢复适配；普通密码/扫码网站的基本登录与操作不等待专用插件。登录状态按本人账号与 bot 保存，不进入普通文件/源码导出。
- PDF 填表/OCR、Office 修改副本与格式转换、图片等插件化处理；按格式提供预览和差异，不承诺通用编辑器编辑所有格式。
- 软件安装状态与重建检查；常用模板依赖及场景依赖分开恢复，避免每次 restart 都重复安装；卸载不得删除共享依赖或用户成果。
- 多 provider、模型能力与费用展示；凭据管理和连接状态保持一致。
- AG-UI 边界适配，与当前/迁移后的 UI 共用同一消息和任务状态；A2UI 继续用于结果、表单与业务卡片。
- Web Push；移动端明确需要后再接 APNs/FCM，不提前要求移动推送账号。

验收：删除记忆后不再检索使用；Cookie 不跨越授权边界；文件原件与处理副本可追溯；协议重连可恢复状态且不重复业务动作；推送权限拒绝不影响站内任务能力。

## 6. 开发与验收纪律

- 每阶段交付可用入口、API、数据库迁移、后台执行及失败处理，不能只做静态页面。
- 新表由 Drizzle 迁移；共享契约由 `@i-bot/types` 定义；修改 packages 添加 changeset。
- 每次实现运行 `pnpm lint`、`pnpm check-types`，针对权限、恢复、幂等、外部授权等实际风险增加测试。
- 使用测试用户、测试部门/群和测试 bucket 进行集成验收；模拟服务用于开发，真实凭据和外部结果单独标记。
- 首期至少验证：跨用户/公司隔离、服务重启、前端关闭、重复事件、迟到回复、token 过期/撤销、R2 签名过期和 sandbox 回收后的下载。
- 真实发消息、修改业务记录和发布需在已明确授权的测试范围内执行；不因为配了 SDK 或 API Key 自动扩大范围。
- 本地只能验证机器在线期间的后台能力。固定在线部署、TLS、数据库备份、密钥保管与日志告警是公司试点发布前的要求。
