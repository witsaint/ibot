# 外部入口的权限、组织信息与个人平台边界

更新日期：2026-10-13。本版本明确 i-bot 支持多个用户独立使用；每个 bot 的私人环境按所有权保护，对外开放的是关联飞书机器人/webhook中的明确业务能力。本文是待实现设计，没有改变 Triage、平台账号或权限数据。

## 1. 产品范围

每位平台用户可以创建自己的 bot、使用其私人会话、连接自己的账号并管理服务。同事可以独立成为平台用户，也可以在飞书经入口触发别人开放的业务；这不授予服务所有者的私人聊天、电脑、历史或凭据访问权。一个人同时拥有平台账号和外部服务请求身份时，两者分别判断。

首期完整 bot 共享、平台协作成员或组织工作区另行定义，其他人独立使用平台不依赖这些能力。所有者在自己的控制台配置外部入口及其权限；通讯录作为管理配置的数据来源，不成为默认面向个人用户的组织目录。

术语见 [CONTEXT.md](../../CONTEXT.md)。

## 2. 两条独立的操作路径

| 路径                        | 身份                         | 使用范围                                                                 |
| --------------------------- | ---------------------------- | ------------------------------------------------------------------------ |
| 本人在 i-bot 操作个人 bot   | 平台登录的所有者             | 本人的连接账号、浏览器和委托任务；正常网页登录不要求安装网站 API 插件    |
| 飞书机器人/webhook 触发业务 | 经入口验证的外部请求人或服务 | 所有者明确开放的业务动作、资源和结果；不能进入个人平台或继承本人全部权限 |

本人连接携程、Google、飞书或其他网站，不改变外部入口允许做什么。外部人员能创建 Linear 需求，不意味着能读本人携程订单、使用 Gmail、查看私人资料或控制电脑。

## 3. Triage 示例

所有者在平台把自己的 bot 与 Triage 应用关联，并开放“查询指定团队需求”“创建需求”等具体业务能力。以下是配置示例，不是现有人员的实际权限：

| 外部人员   | 查询指定团队需求 | 创建需求 | 发起研发执行 |
| ---------- | ---------------- | -------- | ------------ |
| A          | 允许             | 允许     | 另行授权     |
| B          | 允许             | 禁止     | 禁止         |
| 未授权人员 | 禁止             | 禁止     | 禁止         |

A/B 都可以在飞书与机器人对话，但实际调用平台关联能力时，根据当前验证过的发送者检查。B 引用 A 的话、修改 webhook 参数或换另一个工具，仍不能创建需求。非受控普通问答可以继续，不把禁止创建解释成禁止所有对话。

现有 Triage 的 `request-permissions` Skill 在本轮仓库读取中使用 `linear:platform-rd / write` 和另行 `handoff` 的约定；创建/修改等当前归为写入。需要更细区分时，权限动作与工具映射同时调整，不能只改前端名称。[现有规则](/Users/mac/Desktop/workspace/agent/dev-agent/cc-connect/skills/request-permissions/SKILL.md)

复用已有 Triage 权威权限源时，通过适配器查询/编辑；不复制一份同义 ACL 后双向独立维护。入口是否启用、开放动作和资源由本平台保存，Triage 既有业务授权保留其实际约束。未验证生产工具的强制检查，不能仅凭 Skill 说明声称已经实施。

## 4. 通讯录在后台配置中的作用

所有者配置外部调用权限时，用 Triage 获准的通讯录选人、选部门、检查状态。姓名用于显示，规则保存企业、应用和用户标识；不按同名或用户自报的姓名匹配。

首期按指定人员配置即可，不依赖完整部门树；后来增加用户组或已获准部门，明确直属成员/包含子部门。负责人不自动拥有全部能力，明确禁止优先于一般允许。成员变化、离职/冻结和资料过期需在下一次受控动作前按规则检查，不能用旧成员列表扩大权限。

平台上的配置权限属于 bot 所有者，不要求他成为飞书公司管理员；读取的通讯录范围及 API scope 仍服从飞书已有授权。缺少全员范围时，不将“未知人员”推断为公司成员，也不要求先建全公司管理系统。

## 5. 入口认证和外部人员认证分别判断

飞书请求从 SDK/签名验证过的真实事件取得 sender、app、tenant、chat 和 event ID；不使用消息正文、@对象或卡片自报字段作为请求人。Triage 服务向 i-bot 转交时，使用经过验证且带明确目标的服务调用，保存来源与原请求人。

Webhook 的签名只能证明请求来自持有对应密钥的调用方，不自动证明 body.userId 是某个人。若按人授权，来源服务必须经过配置为可信身份来源，并从其原始认证过程核验该人；否则 webhook 只能按获准服务身份及服务级动作执行。不能允许请求体把自己改成有权人员。

外部入口绑定明确 bot 和业务能力，检查动作、实际资源、业务连接、当前规则、必要确认与交付目标。受控动作没有匹配授权时拒绝；权威权限源不可用时不扩大许可。子任务、后台和恢复沿用外部身份，不能切换为所有者权限。[OWASP 授权建议](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)

## 6. 外部请求怎样执行

```text
同事在飞书请求 / 来源服务调用 webhook
                   ↓
验证入口和外部身份 → 检查开放能力及资源规则
                   ↓
建立所有者平台内的外部任务记录 → 受控业务工具执行
                   ↓
保存回执与受控结果 → 经飞书或配置的回调交付
```

外部方通过飞书卡片/回调收到进度、补充信息和结果，无需登录 i-bot。所有者可在平台查看入口记录、暂停和撤销外部调用。

外部任务不注入私人历史、记忆或其他人的受限结果；不开放 root shell、通用个人浏览器或凭据导出。外部能力需要网站执行时，单独限定已开放的业务流程和账号；出现额外动作时交给所有者决定，不自动扩大到整个个人电脑。

当前 owner 路由及一 bot 一活动 sandbox 的隔离保持。新增的是外部调用的受控任务入口，不能把“同公司”加入私人平台访问条件。能否交付数据也要检查：群里发起任务不自动批准向全群公开敏感内容。

## 7. 所有者的管理界面

位置建议：bot 设置 → 外部入口。

- 飞书应用、webhook 来源、绑定 bot、启停状态。
- 明确开放的业务能力、目标团队/项目和业务账号。
- 外部人员/部门或服务身份的允许、禁止、有效期。
- 某个外部身份的有效权限、命中规则和拒绝原因。
- 事件/执行/交付记录、频率与额度、待本人处理的请求。

这是各 bot 所有者管理自己对外能力的控制台。每位平台用户都可以拥有自己的连接、聊天、预览和成果；服务调用者不因使用控制台中的服务而获得所有者的工作区。平台内的服务使用页面与完整 bot 共享分别设计。

## 8. 与本人网站登录的边界

本人账号连接定义能用哪个账号，网站会话决定网页是否已登录，外部规则决定入口能调用哪些业务能力。这三类状态分别处理。

本人在携程网站登录后，通用浏览器可按其委托操作已获网站授权的页面；缺少专用携程 API 插件不作为拒绝理由。已登录但网站要求补充验证、账号自身无权查看某资源或接口不支持时，分别给出真实原因。本人网站登录不开放给飞书外部请求者。

Google/飞书插件提供已实现 API 工具和流程；一个插件可以包含多个产品工具，但安装不等于 API 已授权，也不等于网页已登录。详见 [插件与网站身份研究](./personal-account-plugin-and-browser-auth.md)。

## 9. 验收

- A/B 经同一个 Triage 触发时执行权限不同，B 不能创建；服务授权不允许访问所有者的 bot 工作区、电脑或私人历史。A/B 可以独立登录平台并使用自己的 bot。
- Webhook 持有合法服务密钥但伪造有权用户 ID 时不提升权限。
- 改目标团队、换工具、延后恢复、旧卡片和重复事件均不绕过当前规则。
- 所有者正常使用已登录网站，不因未安装 API 插件或未获外部人员规则授权而被拒绝。
- 本人连接 Gmail/携程后，外部入口仍只有原先明确开放的业务能力。
- 权限撤销、来源失效和交付失败有记录，不重复执行已完成业务。

本版本区分多用户平台、bot 所有权和服务调用权限。平台允许多人独立使用；完整 bot 协作与组织代管尚需另行定义。外部入口权限管理与通用账号登录为待开发能力。
