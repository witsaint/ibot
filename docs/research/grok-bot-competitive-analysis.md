# Grok Bot 竞争调研：功能、用户场景、业务锚点与技术体系

> 调研日期：2026-09-18  
> 资料范围：xAI、Grok、X 与 Cursor 官方页面和官方文档。本文只把官方资料直接支持的内容列为“确认事实”；标有“分析”或“推断”的内容不是厂商承诺。

官方主体说明：Grok Bot 由 SpaceXAI 官方发布，产品运行在 Cursor 云端，使用 Cursor 账号、计费与企业管理体系；它不是 X 内的 Grok 聊天入口，也不是 xAI API 的产品名称。[Grok Bot 发布说明](https://x.ai/news/introducing-grok-bot) [团队与企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises)

## 1. 结论摘要

Grok Bot 的核心不是“更强的聊天机器人”，而是“可以长期负责一个工作结果的电脑代理”。一个用户可以建立多个有明确职责的 Bot。Bot 保留自己的角色、对话和工作记忆，在云端电脑上使用浏览器、文件系统、终端和连接器，并可在用户离线时继续执行。[Grok Bot 概览](https://docs.x.ai/grok-bot/overview)

它目前最有差异的产品组合是：

1. **长期角色**：Bot 不是一次性对话，而是有名字、职责、边界、记忆和固定工作内容的长期对象。
2. **真实工作环境**：工作在 Cursor 云中的持久电脑内完成，可以操作没有 API 或 MCP 的网站，也能通过连接器调用结构化工具。
3. **多 Bot 协作**：多个 Bot 可以并行工作、互发消息、进入群聊并移交任务。
4. **从示范到自动执行**：用户可把成功过程保存为技能，并用定时或事件触发的例程重复执行；部分用户还可录制最长十分钟的浏览器操作，生成技能草稿。
5. **人工控制高风险步骤**：登录、双重验证、验证码和付款确认交给用户接管；发送、发布、购买、删除和生产修改等动作可以要求批准。
6. **面向企业的电脑治理**：每个用户有独立的 Firecracker microVM；企业版提供网络限制、统一初始化、动作记录、审计日志、身份管理和自动审查规则。

最值得关注的商业设计不是单一功能，而是一个完整闭环：**通过 SuperGrok、X Premium+ 和 Cursor 订阅获得用户，通过持续电脑工作消耗按周用量和按需用量，通过连接器、例程和记忆提高迁移成本，再通过企业安全控制向团队和企业扩展**。这是基于官方定价和产品结构作出的分析，不是 xAI 对增长策略的公开说明。[Grok Bot 计划与计费](https://cursor.com/help/grok-bot/plans) [Cursor 定价](https://cursor.com/pricing)

### 关于“Grok Bot 使用哪个模型”

官方企业文档明确写明“Cursor 管理模型选择”，Grok Bot 设置中没有模型选择器；公开文档没有承诺某个固定 Grok 模型、上下文长度、推理强度或路由规则。因此，不能把 xAI API 当前的 Grok 4.6 参数直接当作 Grok Bot 的运行参数。[团队与企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises) [设置与通知](https://docs.x.ai/grok-bot/settings-and-notifications)

## 4. 可落地的用户实践场景

以下场景分为两类：官方建议的产品用法，以及 SpaceXAI 对内部使用结果的公开描述。后者仍是厂商自述，不等同于独立客户案例。

### 4.1 官方文档给出的可实施角色

| 角色         | 输入与工具                                  | 可交付结果                                                     | 建议批准边界                         |
| ------------ | ------------------------------------------- | -------------------------------------------------------------- | ------------------------------------ |
| 销售拓客     | CRM、意向数据、企业网站、邮件、职业社交网络 | 账户评分、联系人优先级、个性化邮件和社交消息草稿、夜间待审列表 | 不自动发送或加入营销序列             |
| 招聘寻访     | ATS、候选人来源、邮件、日历                 | 满足条件的候选人列表、匹配证据、联系草稿和排期准备             | 不自动联系候选人；遵守隐私和地区规则 |
| 广告投放分析 | 广告平台、分析工具、预算表、Slack           | 花费与目标获客成本对比、预算调整建议、Slack 更新草稿           | 不自动改预算或发消息                 |
| 费用管理     | 费用系统、邮件、共享盘、财务表格和制度文件  | 对账汇总、缺失票据与违规项、逐人跟进草稿                       | 不改变报销状态，不自动发送           |
| 产品性能排查 | 监控、分析、事故工具、源代码链接            | 热点判断、截图、直接链接、事实和假设分栏的调查报告             | 不修改告警或生产设置                 |
| 缺陷复现     | 工单系统、测试环境、浏览器和网络工具        | 精确步骤、预期与实际结果、截图、控制台与网络信息、最小测试用例 | 只用测试账号，不接触生产客户数据     |
| 客户健康     | CRM、产品使用、支持、计费、客户成功记录     | 风险与扩展机会排序、证据、原因、下一步建议                     | 不联系客户，不直接修改 CRM           |
| 负责人助理   | Slack、邮件、日历、会议记录、规划文档       | 只保留与优先事项相关的变化、来源、意义、下一步和待决策项       | 不发消息，不改会议                   |

上述场景均来自官方的 [Grok Bot 使用场景](https://docs.x.ai/grok-bot/use-cases)。共同规律是先自动完成“读取、核对、准备和草拟”，再让人在执行外部动作前批准。这是目前最稳妥的落地方式。

### 4.2 SpaceXAI 公开的内部实践

1. **跨系统采购节省**：SpaceXAI 称其 Haggle Bot 接入 Slack、Notion、Drive、Gmail、Hex 和 Ramp，建立约 125 个活跃供应商的工作记录。官方文章称该 Bot 已识别超过 100,000 美元直接节省，其中一次找出 43 个 90 天未使用席位，节省 14,220 美元；另一次识别 85,662 美元年度未使用 SKU。Bot 可自行做内部调查与协调，但花钱、接受条款和对供应商发送内容必须经批准。[采购实践](https://x.ai/news/grok-bot-procurement)
2. **销售、运营和工程交接**：发布文章称内部已有销售 Bot 将通话记录写回 CRM 并准备跟进，运营 Bot 安排新员工座位并处理 Gmail 发票，工程 Bot 复现产品界面缺陷、建工单，再交给调试 Bot。[Grok Bot 发布说明](https://x.ai/news/introducing-grok-bot)
3. **多 Bot 团队**：官方称内部人员会并行使用多个专业 Bot，并由一个“负责人助理”协调；Bot 可在群聊中分工和交接。[Grok Bot 发布说明](https://x.ai/news/introducing-grok-bot)

证据说明：以上是 SpaceXAI 自己的生产使用描述，比单纯的演示提示更强，但仍缺少第三方核验、样本规模、失败率、人工审核成本和总计算成本。不能据此直接推导普通客户也会获得相同收益。

## 5. 业务锚点与商业闭环

### 5.1 官方确认的商业结构

1. **多入口订阅分发**：Grok Bot 包含在付费 Cursor 个人版、Cursor Teams 中，也可通过个人 SuperGrok 或 X Premium+ 账号连接取得使用权。用量按 Cursor 账号计量。[计划与计费](https://cursor.com/help/grok-bot/plans)
2. **按周额度加按需付费**：订阅包含每周额度；额度用完后，可在允许时继续使用按需用量。消耗由代理步骤和 token 决定，不按消息数量计算。[计划与计费](https://cursor.com/help/grok-bot/plans)
3. **团队和企业升级**：团队版提供集中计费、团队市场、共享上下文和使用分析；企业版增加网络、访问、审计、SCIM 和服务支持。[Cursor 定价](https://cursor.com/pricing)
4. **X 生态导流**：连接 X 账号时可创建开发者账号，付费 Grok Bot 用户获得起始 X API 额度，把 X 数据、X 开发者平台与代理工作放进同一入口。[Grok Bot 与 X](https://x.ai/news/grok-bot-and-x)
5. **连接器与模板扩展**：Bot、技能和例程可以复制或分享；团队可以通过插件与 MCP 政策统一提供或限制工具。[创建和管理 Bot](https://docs.x.ai/grok-bot/bots) [团队与企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises)

### 5.2 分析：增长与留存闭环

下面是基于公开产品结构作出的推断：

```text
SuperGrok / X / Cursor 用户入口
          ↓
创建有职责的 Bot，得到第一次跨工具结果
          ↓
保存登录、文件、偏好、技能和例程
          ↓
离线持续运行，按时间或事件自动开始工作
          ↓
更多工作量与更高按需用量
          ↓
多人协作需要企业治理、审计和网络控制
          ↓
团队或企业合同
```

这个闭环有四个业务锚点：

- **结果锚点**：卖点从“回答质量”转向“工作是否进入真实系统并完成”。
- **关系锚点**：产品把代理塑造成长期同事，角色、历史、偏好和例程会持续积累。
- **环境锚点**：登录状态、文件和应用安装保存在用户的云端电脑中，减少重复设置，也提高迁移成本。
- **治理锚点**：个人使用扩大为组织使用后，网络、权限、审批、审计和身份管理成为企业付费理由。

### 6.1 Grok Bot 本身

```text
桌面端 / 移动端
  负责消息、查看进度、批准、通知与人工接管
                │
                ▼
Cursor 云控制面

                │
                ▼

  ├─ 用户内共享文件、浏览器会话、登录和 /workspace
  ├─ shell、浏览器与电脑操作
  ├─ MCP / OAuth 连接器
  └─ 可委派到独立 Cursor Cloud Agent 电脑执行代码任务
```

该图只描述官方明确公开的组件和边界：[团队与企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises)。

关键设计如下：

- 客户端是聊天、查看、批准和接管的轻客户端，实际任务在云端运行。
- 每个用户拥有独立 Firecracker microVM；一个用户的所有 Bot 共享这一台电脑。
- 每个 Bot 有独立角色、对话和屏幕，但不是独立计算与凭据边界。
- Bot 在云端电脑内使用 shell、浏览器和电脑操作，也可调用连接器。
- OAuth token 留在 Cursor 连接器后端，不传给 Bot。
- 编码任务可以委派给独立的 Cursor Cloud Agent 电脑；管理员可关闭该能力。
- Auto Review 是独立的模型审查层，而不是主代理自我批准。
- 模型由 Cursor 选择；公开资料没有给出模型路由、记忆存储实现、代理循环、上下文压缩、浏览器自动化协议、截图模型、任务队列或故障恢复算法。

### 6.3 部署边界

- Grok Bot 的代理电脑运行在 Cursor 云端，而不是 xAI API 客户自行管理的沙箱。[团队与企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises)
- 官方安全常见问题当前写明计算位于美国，不提供本地部署、客户自有云边界部署或自定义基础镜像。[安全常见问题](https://docs.x.ai/grok-bot/security-faq)
- xAI API 的 Web、X、代码执行、Collections 和远程 MCP 工具由 xAI 服务器执行；自定义函数调用则由客户应用执行。[工具概览](https://docs.x.ai/developers/tools/overview)
- Grok Bot 可选访问用户本地电脑，但这是单独授权的能力，默认逐任务批准，可被关闭。[批准、安全与隐私](https://docs.x.ai/grok-bot/approvals-security-and-privacy)
- 企业可限制云端电脑网络访问，也可允许用户把流量经自己的桌面转发，以访问指定网络或使用本地出口地址。[团队与企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises)
- xAI API 的自定义 MCP 默认需要可从公网访问；本地或私网服务需建立隧道。[自定义 MCP 隧道](https://docs.x.ai/grok/connectors/custom-mcp-tunneling)

## 7. 局限、风险和未公开项

### 7.1 官方明确的限制

1. **同一用户内无 Bot 级计算隔离**：所有 Bot 共用一台电脑、文件、浏览器会话和登录。不能用不同 Bot 隔离不同客户或不同敏感级别的数据。[常见问题](https://docs.x.ai/grok-bot/faq)
2. **网站自动化不保证成功**：网站可能阻止自动化、使登录失效、弹出验证码或要求人工确认。[常见问题](https://docs.x.ai/grok-bot/faq)
3. **高风险批准不是撤销机制**：批准只控制待执行动作，不能撤销已经完成的工作；Auto Review 也不能替代最小权限。[批准、安全与隐私](https://docs.x.ai/grok-bot/approvals-security-and-privacy)
4. **自动审查不是完整副作用审查**：官方安全常见问题明确说明，Auto Review 不覆盖部分记忆写入和多数设置修改等所有副作用。[安全常见问题](https://docs.x.ai/grok-bot/security-faq)
5. **训练示范覆盖有限**：示范教学逐步开放，当前只录制一次最长十分钟的浏览器流程，生成的是需复核的技能草稿。[技能与例程](https://docs.x.ai/grok-bot/skills-routines-and-automations)
6. **例程有产品限制**：每个 Bot 最多 50 个例程，每个例程只保留最近 20 次执行；长时间无人使用时，系统可能询问是否继续并在无响应时暂停例程。[技能与例程](https://docs.x.ai/grok-bot/skills-routines-and-automations)
7. **必须使用云端存储**：Legacy Privacy Mode 不支持 Grok Bot。[批准、安全与隐私](https://docs.x.ai/grok-bot/approvals-security-and-privacy)
8. **企业能力不是团队版默认能力**：网络限制、强制自动审查、动作记录、批量电脑管理等多项能力仅企业版提供。[团队与企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises)
9. **企业团队当前没有独立的 Grok Bot 费用上限**：使用账号级按需控制，只能在仪表盘查看产品拆分。[团队与企业架构](https://docs.x.ai/grok-bot/teams-and-enterprises)

### 7.2 公开资料没有说明的内容

截至调研日期，官方公开资料没有清楚说明以下内容：

- Grok Bot 实际使用的固定模型、模型组合、路由策略、上下文长度和推理参数。

### 9.3 i-bot 已经形成的优势

1. **Bot 级隔离更清楚**：i-bot 的一个 Bot 对应一个 Sandbox，登录、文件和运行环境不会自动暴露给同一用户的其他 Bot。Grok Bot 的共享电脑有更低的重复登录成本，但官方明确要求不要把 Bot 当作安全边界。对需要多个客户账号、多个业务身份或不同敏感级别的工作，i-bot 的设计更容易解释和审计。
2. **人工接管链路已经贯通**：用户可以观察桌面、接管鼠标和键盘，服务端会阻止代理继续发送图形界面操作。这个能力与登录、双重验证和复杂页面处理直接相关，不只是演示界面。
3. **浏览器、桌面和终端形成互补**：网页任务优先使用稳定的 DOM 操作，必要时再使用坐标操作，文件和脚本工作使用终端。这比只依赖截图和坐标更稳定，也比只依赖 API 覆盖更多网站。
4. **一次工作可以沉淀为技能**：对话中的工具记录可整理为可审核的技能草稿，再保存到 Postgres 并在 Sandbox 重建后恢复。这个方向与 Grok Bot 的“先完成一次，再保存方法”一致。
5. **密钥和租户隔离设计较完整**：密钥加密保存，模型只能看到引用名；Bot 级密钥可覆盖用户级密钥。MCP 的远程凭据也在服务端处理。
6. **并发规则已经明确**：前台回复、后台终端任务、需要桌面的后台任务和人工接管分别处理，避免多个控制方同时操作一个桌面。

## 10. 技术体系差异

| 层面           | Grok Bot                                                | i-bot                                                                                   | 影响                                                                             |
| -------------- | ------------------------------------------------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| 计算隔离单位   | 每用户一台持久 Firecracker microVM；用户内多个 Bot 共享 | 每 Bot 一个 PPIO Sandbox，经 AIProxy 创建和连接                                         | i-bot 隔离更强；Grok Bot 登录复用和资源利用率更好。                              |
| 计算持久性     | 持久磁盘和长期在线是产品默认                            | Sandbox 支持保活、重连和重建；上游仍有时长与重启约束                                    | i-bot 必须把可恢复状态放到数据库和对象存储，不能把 Sandbox 当永久主存储。        |
| 模型选择       | Cursor 管理，没有用户模型选择器                         | 用户自带 Anthropic 或兼容网关密钥，每个 Bot 可选模型                                    | i-bot 更透明、更灵活，但配置成本和兼容责任更高。                                 |
| 模型提供方抽象 | 未公开                                                  | 文档称提供方无关，但当前代码固定使用 `createAnthropic`，模型列表也按 Anthropic 格式读取 | 当前实现并非真正的多提供方，需要统一接口后才能安全接入 Grok、OpenAI 或其他模型。 |
| 代理编排       | 未公开；公开产品包含例程、批准、多 Bot 和恢复           | 主循环直接使用 Vercel AI SDK；后台任务和状态管理是自研内存对象                          | 当前能快速迭代，但缺少跨进程恢复、持久队列和完整工作流状态机。                   |
| Mastra         | 未公开                                                  | `AGENTS.md` 把 Mastra 定为锁定架构，依赖已安装，但当前主运行链路没有使用 Mastra         | 目标架构与实际代码不一致，后续开发会持续产生两套理解。                           |
| 聊天界面       | 自有桌面和移动端客户端                                  | `AGENTS.md` 要求 assistant-ui，当前实际使用 `@ai-sdk/react` 和自有组件                  | 需要明确选择并更新文档或完成迁移，不能继续保持名义接入。                         |
| 连接器         | OAuth token 留在连接器后端，企业可配置策略              | MCP 凭据加密保存，可连接远程或 Sandbox 内服务                                           | i-bot 有协议基础，缺少授权、目录、可见性和管理体验。                             |
| 技能召回       | 公开说明有技能启停和跨 Bot 使用，召回细节未公开         | 每次加载该 Bot 的全部技能和全部公共技能，没有按任务筛选                                 | 技能数量增加后会扩大上下文并降低选择准确率。                                     |
| 消息和文件     | 文件作为完整产品能力管理                                | 消息结构和附件表已定义，但前端仍把二进制 data URL 直接存进消息                          | 这是上线前必须修复的数据和成本问题。                                             |
| 任务事件       | 支持离线例程、历史和通知                                | SSE 事件总线只在单个 API 进程内；数据库是结果来源                                       | 多实例部署前需要共享事件通道和可恢复任务执行器。                                 |
| 风险控制       | 独立 Auto Review、逐动作批准、企业规则                  | 系统提示、租户校验、密钥隔离、人工接管                                                  | i-bot 的数据边界较好，但外部动作控制不足。                                       |
| 可观测性       | 企业动作记录、审计和 OpenTelemetry                      | 有日志和任务状态，消息 metadata 尚未形成统一的用量、时延、模型和结果记录                | 无法稳定计算成功率、成本和失败原因。                                             |

### 10.1 两个需要尽快处理的架构不一致

1. **“提供方无关”与 Anthropic 固定实现不一致**：共享类型允许每个 Bot 写任意模型名，但真正的模型创建和模型目录都使用 Anthropic 接口。建议先定义 `ModelProvider` 接口和能力声明，再增加新的提供方；不要只把 Grok 模型名填进现有输入框。
2. **“Mastra + assistant-ui”与当前运行链路不一致**：这不是单纯的依赖缺失。它会影响记忆归属、暂停与恢复、消息协议、后台任务和前端组件选择。需要做一次明确决定：要么完成锁定架构的接入，要么修改架构文档并删除未使用依赖。建议以“能否提供持久任务恢复和批准状态”为判断标准，而不是为了框架名称迁移。

## 11. 业务定位建议

### 11.1 不建议把目标定义为“做一个更小的 Grok Bot”

Grok Bot 已经利用 SuperGrok、X、Cursor、多端客户端、连接器市场和企业销售形成完整分发体系。i-bot 在短期内追平通用问答、语音、图像、视频、移动端、多 Bot 群聊和企业管理，会分散资源，而且无法形成清楚的购买理由。

建议把 i-bot 的核心承诺定义为：

> **一个 Bot 对应一个隔离的业务身份和电脑环境，持续完成需要登录、跨网页和人工确认的重复工作，并留下可审核的结果。**

这个定位把当前最成熟的能力放在同一条链路上：独立 Sandbox、浏览器与桌面操作、人工接管、密钥、后台任务、结果记录和技能复用。它也明确区别于 Grok Bot 的“一个用户的所有 Bot 共享电脑和登录”。

### 11.2 首批场景应满足四个条件

1. 每周或每天重复，不是一次性问答。
2. 需要登录一个或多个网页系统，只有 API 不能完整覆盖。
3. 结果可以客观验收，例如表格、工单、草稿、截图、对账差异或测试步骤。
4. 外部修改可以先停在待审核状态，避免一开始就承担自动发送、付款或生产修改风险。

按当前能力，建议优先验证两个方向：

- **后台运营核对与待审草稿**：跨 CRM、工单、财务后台、邮件或表格完成读取、核对、分类和草拟，最终由人确认发送或修改。
- **网页缺陷复现与验收**：在独立测试账号和环境中复现问题，返回步骤、截图、控制台信息和验收结论，再由人决定是否建单或发布。

前者更接近持续付费的业务工作，后者更容易用成功率和证据完整度做早期质量验证。建议用同一套底层能力服务这两个方向，但市场入口先只选择一个。

### 11.3 应该保留和不应该照搬的设计

应保留：

- 一 Bot 一 Sandbox，把它作为敏感账号和客户环境隔离能力。
- 浏览器优先、桌面补充、终端处理文件的工具顺序。
- 人工接管与代理操作互斥。
- Postgres 保存技能和业务状态，Sandbox 只做运行环境。
- 用户自带模型密钥，适合需要模型和成本自主权的客户。

不建议现在照搬：

- 为降低成本改成同一用户的全部 Bot 共享一台电脑。这样会削弱当前最明确的安全差异。
- 先做语音、图像生成或视频生成。它们不是完成网页业务工作的主要阻塞点。
- 先做复杂的多 Bot 组织图。当前更重要的是让一个 Bot 可以稳定、可恢复地完成一项工作。
- 在没有逐动作批准和恢复机制前开放自动发送、付款、删除或生产修改。

## 12. 优先级建议

### P0：先让“离线完成一项工作”可信

1. **持久任务执行**：把后台任务从 API 进程内对象迁移到可恢复的任务执行器。任务需要保存步骤、租约、心跳、重试、取消和最终状态。API 重启后应能继续或明确恢复，而不是只剩一条 `running` 数据。
2. **共享事件通道**：用可跨实例的发布订阅或数据库事件替代进程内事件总线，确保多实例和重启后的状态一致。
3. **文件完整链路**：接通 R2 预签名上传、附件行、短期下载地址和清理；消息只保存对象引用。增加提供方能力过滤，视频不能直接进入不支持视频的模型请求。
4. **逐动作批准**：为发送、发布、购买、删除、权限和生产修改定义统一风险类别。工具执行前生成明确的目标、参数和影响，用户允许一次或拒绝；批准状态必须持久化。
5. **结果记录**：统一保存模型、token、时延、工具调用、失败类型、人工接管、结果文件和来源链接。没有这些数据就无法判断业务是否成立。
6. **解决架构文档偏差**：完成 Mastra 和 assistant-ui 接入，或正式修改锁定架构。模型提供方也要从 Anthropic 固定实现改为明确的提供方接口。

### P1：建立重复使用和主动工作

1. **例程**：先支持固定时间和简单 Webhook 两类触发；提供启停、测试运行、最近记录、时区和失败通知。
2. **可审核结果**：让 Bot 返回文件、截图、来源、已完成动作、待批准动作和未解决问题的固定结果结构。
3. **技能选择**：先用名称、描述和关键词做确定性筛选，再考虑向量检索。不要每次把所有技能放进上下文。
4. **新用户起步**：提供少量有明确产出的 Bot 模板，例如“网页缺陷复现”和“每周后台核对”，并给出示例任务、所需账号和禁止动作。
5. **完成与阻塞通知**：Web 推送或邮件只在完成、失败或需要人工输入时通知，避免发送无意义的过程消息。
6. **MCP 管理界面**：支持添加、测试、启停、工具白名单和 OAuth；Bot 自行绑定仍应经过用户确认。

### P2：在单 Bot 价值成立后扩展

1. 不同 Bot 之间的消息、任务移交和群聊。
2. Bot 复制、团队模板和技能共享。
3. 组织、角色、SSO、网络出口限制、审计导出和用量预算。
4. Grok 或其他模型提供方，以及 Web Search、X Search 等专用实时信息工具。
5. 移动端查看、批准、接管和通知；不必一开始复制完整桌面体验。

## 13. 90 天建议计划

| 时间        | 主要目标             | 完成标准                                                                                                                                                             |
| ----------- | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 第 1—30 天  | 可靠性和数据闭环     | 后台任务可在服务重启后恢复；文件进入 R2；不支持的视频不会进入模型；高风险工具必须等待持久化批准；每个任务有统一运行记录。                                            |
| 第 31—60 天 | 重复执行和可验收结果 | 有定时例程、失败通知、最近运行记录；至少两个固定场景能输出来源、截图、文件和待批准动作；技能按任务筛选。                                                             |
| 第 61—90 天 | 小范围真实用户验证   | 选择一个主要场景，与 5—10 个真实用户连续运行四周；统计完成率、人工接管、修改次数、单位任务成本和每周重复使用。根据数据决定是否进入多 Bot、团队管理和更多模型提供方。 |

## 14. 建议跟踪的业务和技术指标

不要用消息数或创建 Bot 数作为主要成功指标。建议至少跟踪：

- 首次成功任务所需时间。
- 任务完整完成率，以及只完成一部分的比例。
- 有证据可验收的结果比例。
- 用户修改一次后第二次成功的比例。
- 技能保存率、技能再次使用率和例程创建率。
- 例程按时成功率、重试率和连续失败次数。
- 需要人工接管的任务比例、接管原因和恢复成功率。
- 需要批准的动作比例、批准等待时间和拒绝率。
- 每个成功任务的模型成本、Sandbox 成本和总耗时。
- Sandbox 空闲占用时间和重建成功率。
- 第 1 周和第 4 周仍在重复运行同类工作的用户比例。

## 15. 最终判断

i-bot 不是从零开始。它已经具备 Grok Bot 最难演示清楚的几项基础能力：真实电脑、网页与桌面操作、人工接管、后台任务、密钥隔离和经验保存。当前差距主要不在模型能力，而在把这些能力组织成一个用户可以长期信任的产品：任务必须可恢复，外部动作必须可批准，结果必须可验收，重复任务必须能按时主动运行。

最合理的策略不是扩大功能清单，而是先证明一条完整链路：**用户交给一个隔离 Bot 一项重复网页工作，Bot 在用户离线时执行，遇到敏感步骤请求批准，最后交付带证据的结果，并把成功方法保存为下一次可复用的技能。** 这条链路一旦稳定，例程、连接器、团队模板和多 Bot 协作才有清楚的扩展顺序。
