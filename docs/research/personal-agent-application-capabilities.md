# 个人 agent 的应用层能力评审

日期：2026-09-30（Asia/Shanghai）。本次对照 i-bot 当前工作目录、OpenMuse 官方固定源码、AG-UI 与 Google 官方文档。只完成研究和设计补充，没有实现下文建议，也没有运行真实账号、模型或部署验证。

## 结论

个人 agent 应提供交互、目标执行、应用连接、凭据、人工参与、工作区、文件成果、通知和管理能力。Gmail、日历、内部工单等应成为可安装能力的应用场景，同时具备独立的账号连接管理。安装一个插件与授权一个账号是两件事。

AG-UI 可作为前端与 agent 后端的交互接口；它不自动提供公司平台授权、可靠后台执行或文件保存。下载动作本身不要求 R2，但长期成果需要对象存储；本仓库已约定 R2 为持久二进制成果的存储位置。

已有资料：[目标执行与成果评审](./personal-agent-harness-review.md)、[AIProxy 轻部署评审](./aiproxy-lite-deployment-review.md)、[OpenMuse 能力核实](./openmuse-capabilities.md)。

## 1. OpenMuse 的参考价值和边界

官方仓库快照：`d0b3a6b3ea461bc938a5dea6c46e65eefdb1b933`。它已有任务、计划与证据、人工输入/审批、通知列表、可编辑个人记忆、浏览器、PDF 流程和可选 Linux 的实际代码。当前为单 owner alpha；Google、Intelligence 跨设备以及真实模型开放任务的集成验收仍待完成。演示的模型部分使用 AI Mock，不能据此认为真实账号上的所有流程已经可靠。[官方验收说明](https://github.com/CopilotKit/openmuse/blob/d0b3a6b3ea461bc938a5dea6c46e65eefdb1b933/docs/VERIFICATION.md)、[路线图](https://github.com/CopilotKit/openmuse/blob/d0b3a6b3ea461bc938a5dea6c46e65eefdb1b933/ROADMAP.md)

尤其应区分：

- 人工输入和审批会阻塞当前任务，worker 可执行其他任务；没有证实通用的当前任务非阻塞提问。我们的设计仍需同时支持阻塞与非阻塞两种模式。
- 文件能力主要为 PDF 导入、浏览器 PDF 下载和文本编辑；可选 Linux 不是完整图形桌面。
- 其当前版本未发现自己的通用 skills/plugin 安装体系或 A2UI renderer；展示采用自定义工具卡片。
- 有应用内通知记录，尚无 APNs/FCM 设备推送。所有运行模式还要求 CopilotKit Intelligence key。

具体源码证据及已实现/待验收区分见 [OpenMuse 能力核实](./openmuse-capabilities.md)。借鉴应以具体流程为单位，不直接搬用其身份与存储模型。

## 3. AG-UI、A2UI 与现有前端如何共存

AG-UI 定义 agent 后端到客户端的事件交互，包含文本、工具调用、状态快照/增量等。A2UI 用于描述由预批准组件构成的界面，两者职责可以结合。[AG-UI 介绍](https://docs.ag-ui.com/introduction)、[事件说明](https://docs.ag-ui.com/concepts/events)

当前 i-bot 使用 AI SDK UI stream，并已使用 A2UI；没有发现 AG-UI 依赖或完整协议接口。建议保留当前前端传输，通过边界适配支持 AG-UI 客户端，先验证需要的交互能力。是否整体迁移前端，还应处理之前发现的 Mastra/NestJS/assistant-ui 文档与运行实现差异。

同一持久状态对两个客户端输出：

```text
目标 / 会话 / 执行 / 人工请求 / 成果记录
                    ↓
         AI SDK UI 或 AG-UI 交互接口
                    ↓
     Web / 后续移动端 / 其他经授权的客户端
                    ↓
        A2UI 卡片、任务状态、文件及预览
```

消息仍保存现有唯一 `messages.parts` 格式；协议差异在边界转换，不额外建立第二套权威会话记录。数据库状态决定目标是否完成；流结束、工具参数结束等交互事件不能代替业务验收。

AG-UI 接口还需要接入服务器授权、请求 ID、事件顺序、重新连接后的快照以及重复动作处理。持久执行、离线继续、通知送达由平台负责，不能只添加 SDK 后就宣称具备。

## 4. 插件应覆盖应用领域，账号连接单独管理

### 三类内容共用现有插件体系

| 内容            | 示例                                         | 用户关注                                         |
| --------------- | -------------------------------------------- | ------------------------------------------------ |
| 通用 agent 能力 | skills、专家、MCP、代码/浏览器工具、卡片模板 | 安装后 agent 能调用哪些能力                      |
| 应用连接能力    | Gmail、日历、飞书、GitHub、工单、知识库      | 连的是哪个账号，能读写什么，授权是否有效         |
| 具体工作流程    | 邮件附件填写、异常日报、需求同步、网页创作   | 输入什么，何时触发，成果是什么，哪些步骤要人确认 |

应用连接插件可以包含 tools、skills、UI 模板、事件说明和所需权限；插件配置绑定独立的 connectionId，而不是携带账号 token。一个用户可授权多个账号，一个账号可以被明确授权给多个 bot，凭据不随插件导出或复制。

安装插件之后，可能显示“未连接账号”；授权账号后，某个 bot 仍可能显示“未启用”；实际使用写入操作时还可能显示“需要确认”。这些状态需要分别展示。卸载插件、解除账号连接、停止自动化也是不同动作，不能隐式捆绑删除用户数据。

安装后注册的能力是否下一回合才可用，遵守现有固定 toolset 行为；不要把成功安装等同于当前执行已经获得工具。

### Gmail 的完整产品范围

建议从只读邮件、线程和附件开始，然后加入应用内回复草稿、确认后发送、明确筛选条件的新邮件触发，以及邮件/附件/草稿的结果卡片。应用内草稿与已同步到 Gmail 的草稿要分别标记。

Google OAuth 有服务端离线授权及刷新机制；Gmail 区分 read、compose、send 等 scope，部分 scope 有审核要求。应用应按所需能力申请权限，不因为 UI 中选择“只读”就忽略实际 token 权限。[OAuth 官方说明](https://developers.google.com/identity/protocols/oauth2/web-server)、[Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes)

平台同时需要两个判断：账号授予的 API 权限，以及用户对本次具体动作的授权。OAuth 的发信权限不等于批准每一封邮件；确认内容应绑定收件人、正文、附件、账号和版本。

Gmail 变化通知通过 Cloud Pub/Sub 与 watch 接入，需要维护订阅续期，再查询变化；不能直接套用我们当前自定义签名 webhook。后台运行也不应按每封邮件无条件唤醒昂贵 agent，而是先确定性筛选、去重，再建立目标。[Gmail push 官方说明](https://developers.google.com/workspace/gmail/api/guides/push)

## 5. 凭据管理与网站登录管理

| 配置                   | 归属与使用                                                  | 需要的界面                                 |
| ---------------------- | ----------------------------------------------------------- | ------------------------------------------ |
| 模型 Key / provider    | 用户模型调用，目前一用户一份凭据且执行走 Anthropic provider | 配置、测试、默认模型、用量与限额           |
| 平台 AIProxy / R2 凭据 | 服务器基础设施                                              | 管理端配置，不成为用户插件的秘密           |
| 公司 API Key / token   | 用户或经授权组织的外部服务身份                              | 脱敏状态、权限、作用 bot、轮换与撤销       |
| OAuth connection       | 指定用户与外部账号、scopes、refresh 与状态                  | 连接、补充授权、重新连接、断开、多账号选择 |
| 网站浏览器状态         | 指定账号与 bot 的网页会话                                   | 登录/失效状态、人工接管、清除及恢复        |

既有模型凭据和 tenant secrets 可以复用，OAuth 与连接生命周期仍需实现。网站 Cookie 不代替正式 API 授权；i-bot 自身登录、外部网站登录与模型凭据也不混用。凭据只由服务器在需要时解析，普通文件、记忆、插件包和模型上下文不保存秘密值。

## 6. 通知是持久状态，不只是 SSE 提示

现有 SSE 是进程内通知总线，用于同步正在打开的界面；数据库是权威状态。自动化已有未读结果和回调，但还没有飞书、邮件、操作系统推送等完整通道。

建议建立统一通知记录，再投递到用户选定的通道：

- 需要人处理：必要输入、审批、登录失效，直接进入对应请求。
- 结果与异常：目标完成、失败、达到预算、监测到有意义的变化。
- 非阻塞提问：任务仍在运行，可在通知列表补充，不显示整项任务已经暂停。

通知关联目标/任务/请求/成果，保存未读、发送及投递失败状态。支持合并重复事件、安静时段、通道偏好、失败重试。任务执行和通知发送分开；补发通知不能重新发邮件或重复创建工单。正常中间步骤不需要条条推送。

飞书/邮件适合内部通知；Web Push 或后续 APNs/FCM 用于前端关闭后的设备通知。添加通道仍需独立授权、客户端许可与送达验证，不能用“已写入通知列表”代替“已推送到设备”。

## 7. 文件、编辑、处理和安装

### 文件操作

当前聊天文件选择只接受图片/视频，并暂存为 data URL；attachments 与 R2 基础已存在，但没有通用 PDF/CSV/Office 文件上传、sandbox 输入准备和下载入口。因此“文件能力已有底层”与“用户能完整交付文件”要分开。

建议提供：

- 用户上传：图片、PDF、CSV、Office 文档、源码包等，保留原件与文件信息。
- 外部下载：网页或应用附件进入对应任务的工作目录，关联来源、账号及目标。
- 预览：文本、代码、图片、PDF、CSV/表格，格式不支持时仍可下载原件。
- 编辑：文本/代码直接编辑；文档默认生成修改副本，展示差异、版本及导出。PDF 填表、OCR、Office 转换是具体处理能力，不承诺一个通用编辑器支持全部格式。
- 交付：登记可下载成果、网页或业务记录，把用户上传的原件与生成副本分别标记。

同时修改同一文件要检查版本或任务所有权；代码由子任务分开修改时可以使用 worktree。父会话合并结果与文件合并仍是两个独立过程。

### 安装与下载软件

需区分用户下载成果、agent 下载网页附件、安装插件，以及 sandbox 安装软件。现有 setup step 支持 apt/pip/npm/cmd/download，不代表已完成通用软件管理界面。

插件安装应显示内容、所需连接、脚本与依赖，支持 inspect、安装、启用/停用、状态和日志。软件依赖有明确版本、检查和幂等恢复方式；运行进度与失败原因可见。常用基础依赖可在已有模板策略中预装，场景依赖按需安装，避免每次恢复桌面都无条件重装。

任意插件不能改服务器基础设施配置；可执行依赖仍运行在对应 bot 的 sandbox。卸载只清理归属于该插件的资源，不能移除其他项目共享的依赖或用户成果。

## 8. 下载是否需要 R2

### 临时下载可以不经过 R2

服务器先校验 bot 和文件归属，再从 sandbox 文件 API 读取内容，将它作为附件响应给浏览器。现有 `handle.files.readBytes` 可作为小文件读取基础，但还需要用户下载路由、文件范围检查、文件名/类型等响应处理。大文件应使用流式读取或对象存储，不能用现有一次性 readBytes 无限制加载。

这种方式适合工作区中的临时文件和当前在线 sandbox 的即时导出。sandbox 不在线、文件被删除或回收后，下载将不可用；文件路径不是长期成果。

### 长期成果按项目约定使用 R2

```text
用户输入 / 外部下载
        ↓
sandbox 工作副本 → 编辑、处理、构建
        ↓
用户交付成果 → R2 私有对象 + 数据库元数据
        ↓
经平台归属校验的签名下载 / 预览 / 分享
```

R2 存文件字节，数据库存 owner/bot/目标/执行关联、object key、文件名、MIME、大小、版本等。消息引用同一成果记录；不把二进制塞进消息 JSON。当前 attachments 模型与消息绑定，若目标成果先于最终消息产生，需要沿既有契约扩展关联，而不是复制第二套文件/消息表示。

R2 是当前实现选型；可通过存储接口将来替换为其他对象存储。直接 sandbox 下载是一条临时交付路径，不能绕过“已保存会话成果的字节位于对象存储”这一仓库约定。

### 什么时候保存

用户上传的原件、明确交付的结果、被消息引用的持久媒体、需要分享/历史恢复的文件进入 R2。构建依赖、缓存、临时文件保留 sandbox，不必全部同步。

下载签名 URL 有效期与对象保留期限是两件事。链接过期时重新鉴权生成；文件保留期限、删除和分享撤销由平台规则处理。浏览器 profile、密钥与 `.env` 不进入普通源码或成果包。

## 9. 三个能验证完整产品能力的场景

### 邮件附件处理

Gmail 连接 → 读取选定邮件/PDF → 保存原件与来源 → 创建目标 → 请求缺少字段 → 生成副本 → 展示预览与差异 → 人确认回复内容 → 发送 → 保存回执 → 通知并提供下载。

等待字段时，依赖这些字段的部分阻塞；其他独立工作可继续。可选偏好可作为非阻塞提问。确认发送必须与实际内容和账号绑定，不能被超时自动绕过。

### 公司数据报告

定时或平台事件 → 确定性筛选与去重 → 查询经授权数据 → 分析并形成图表/表格 → 提供来源与可下载文件 → 有异常时通知 → 需要写回的操作等待对应确认。

### 网页或内部服务交付

用户主题或任务材料 → 现有网页插件 → `/root/projects`、独立 design.md → 开发与预览 → 必要人工确认 → AIProxy 轻部署 → endpoint 验证 → 版本与源码成果保存 → 链接和下载展示。

## 10. 优先级与验收

建议先完成目标/人工请求与文件成果，再接一个真实应用和一条通知通道，验证完整流程；AG-UI 多端适配与更多应用随后扩展。这是评审优先级，不是本轮实现承诺。

应验证：

- 同一份状态能被现有 Web 与新增协议客户端正确读取；断线重连不重复动作。
- 阻塞/非阻塞请求影响范围准确，回复对应正确任务；未确认的写入不执行。
- 安装插件后能明确看见未授权、已授权、未启用、依赖失败等状态。
- 多账号不混用，刷新与撤销生效；后台任务不会借用其他用户或平台模型 Key。
- 输入文件、工作副本与成果明确关联；原件不因编辑被覆盖。
