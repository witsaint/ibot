# 基于飞书的个人 agent：任务执行、账号身份与持久保存

日期：2026-10-13。本文根据用户对公司内部使用场景的澄清，修订默认界面与开发重点。内容为待实现设计；当前 i-bot 的 OAuth 连接、持久个人任务、通用登录状态恢复等未按本文实现。

## 1. 产品用途

每个人在 i-bot 有自己的 bot，可从 Web 或飞书交给它一件事。bot 使用本人明确连接的账号和获准的应用能力，打开网页或调用 API，完成任务、留下成果，并回到原对话通知本人。网页关闭不影响已委托任务；需要本人登录或补充信息时，保存进度并等待，其他独立工作可继续。

飞书是任务入口、获准能力来源和结果通知通道。通讯录是这些能力的辅助信息，用于确定“发给谁、找谁负责、哪个部门的人”；首期不设置默认组织资料页面。只有任务要选人时，展示人员搜索或允许范围内的部门选择；用户明确要求看组织结构时，可返回树状结果。完整通讯录同步不作为个人使用前提。

最新边界：平台及个人电脑只由 bot 所有者本人使用，不提供同事的平台入口或 bot 分享。本人可以关联开放给其他人的 Triage 飞书应用或 webhook；通讯录用于该外部入口后台的人员/部门规则，例如 A 可经 Triage 创建需求、B 不可创建。外部方只得到获准业务结果，不进入平台、电脑或个人账号。[外部入口设计](./bot-access-and-organization-design.md)

独立 i-bot bot 包含自己的 owner、对话、目标、偏好、账号连接授权、成果与 sandbox。长期身份和任务状态保存在平台，sandbox 用于执行工作。替换 sandbox 不应删除平台上的目标、连接和已保存成果；原 sandbox 临时文件或浏览器会话能否恢复，需要分别检查。

## 2. 三种操作身份

| 操作                                     | 账号身份来自哪里                    | 要保存与核验什么                                                                         |
| ---------------------------------------- | ----------------------------------- | ---------------------------------------------------------------------------------------- |
| Triage 机器人发通知/回复、查询获准通讯录 | 已发布飞书应用及机器人 token        | 来源应用和企业、可信消息发送者、所选个人 bot、获准数据范围；消息显示机器人身份           |
| 本人授权的飞书 API 操作                  | 本人的 OAuth 连接及实际 user scopes | i-bot owner、app/tenant/user、授权范围、到期时间、指定 bot；动作是否支持用户身份单独核实 |
| 浏览器打开飞书或其他系统的网页执行       | 对应网站认可的浏览器会话            | 网站 origin、实际登录账号、所选 bot、保存/恢复状态、当前任务和操作授权                   |

机器人接收到本人发来的请求，只能证明请求人；它不自动获得本人的 API token 或网站登录态。个人飞书 OAuth 也不会自动生成飞书网页登录 Cookie，或让所有公司内部网站登录。内部系统有自己的飞书 SSO 时，由该系统的正式登录流程建立会话；否则由本人完成对应网站登录。

普通机器人发送不能通过填写姓名或头像变成本人发送。以本人身份发消息须使用官方支持的接口、用户授权及该动作所需 scope，或在本人已登录网页中执行用户明确委托的操作；这两种方式分别验收。具体 API 与限制见 [飞书消息身份核实](./feishu-message-identity.md)。

官方普通消息创建/回复接口支持用户令牌；本人发送需 `im:message` 和 `im:message.send_as_user` 等对应权限，仍受收件人、群和消息类型限制。首次接入分别验证单聊、群聊和回复，不把机器人已能发送当作本人权限已开通。[创建消息](https://open.feishu.cn/document/server-docs/im-v1/message/create)、[回复消息](https://open.feishu.cn/document/server-docs/im-v1/message/reply)

所有者把自己的 bot 与 Triage 飞书应用/入口明确关联。本人经飞书委托时按本人的已核验身份执行；外部人员触发时按入口开放规则执行，不能把对方变成本人的平台身份。外部人员无需创建 i-bot 账号，也不能使用其他所有者的环境。

## 3. 安全保存个人身份

### 身份绑定

用户在已登录的 i-bot 中发起连接，服务端生成一次性授权会话，保存 owner、目标 bot、state、有效期和回跳位置。飞书授权回调校验 state、交换 code，并从官方用户信息接口取得身份；绑定应用、企业和用户标识。相同姓名、邮箱或用户粘贴的 OpenID 都不用于自动合并账号。

复用 Triage 入口时，sender 身份从其验证过的事件获得，并先区分本人请求与外部请求。卡片里的 userId、botId 只能作为待核验参数，不能决定凭据所属人；外部请求不能继承本人的 OAuth 或通用浏览器。入口绑定明确 bot/能力，不按最近一条对话猜测。

### OAuth 授权的存储与执行

- 服务器持久保存连接记录：owner、应用、企业、用户标识、实际 scopes、作用 bot、授权时间、access/refresh 到期时间、连接状态及撤销记录。
- token 加密保存，解密密钥由后端秘密配置管理，备份包含密文与必要元数据，不包含明文 token。平台应用 Secret 与个人授权分别管理。
- 模型使用连接名称/ID 调用工具；服务端先检查 owner、bot、scope 和当前操作授权，再使用相应 token。API token 不写入提示词、网页 URL、普通日志、插件包或开发 sandbox。
- 后台刷新不依赖聊天窗口或 sandbox 在线。同一连接串行刷新，成功后原子保存新的令牌与到期时间；失败区分临时错误和需要重新授权，不反复消费同一一次性 refresh token。
- 断开连接后停止其后台刷新和新调用，删除或撤销所保存凭据，并按飞书实际支持的方式处理远端授权。明确区分本地删除与飞书侧撤销，不能只隐藏 UI 就声明撤销成功。

官方规则：后台刷新依赖应用已开通且本人授权的 `offline_access`；有效期按响应；refresh token 单次轮换；授权达到 365 天需重新授权。应用原有用户权限不足时，本人授权不能添加新的应用权限。[个人连接研究](./feishu-personal-account-connection.md)、[官方刷新文档](https://open.feishu.cn/document/uAjLw4CM/ukTMukTMukTM/authentication-management/access-token/refresh-user-access-token-v3)

### 网站登录的存储与执行

通用网站登录是个人电脑的基础能力。本人在携程等网站登录后，可以按网站实际权限浏览、查订单、填写和执行获准任务；不需要网站 API 插件或外部人员白名单。缺少 API 授权、网站要求额外验证、网站拒绝访问和浏览器任务失败分别展示，不能统一写成“没有权限”。[插件与网站登录研究](./personal-account-plugin-and-browser-auth.md)

本人在指定账号和 bot 的浏览器中扫码、登录或完成设备验证。登录期间暂停 agent 对敏感步骤的自动操作和录屏；完成后检查目标域名与实际登录账号，再接着处理任务。若需持久保存，用户选择保存该网站状态；加密保存可恢复的数据和版本，较大快照位于私有 R2、数据库只保存引用。恢复后验证登录是否仍被网站认可，失败时交给本人重新登录。

网页登录状态必须和项目文件分开，不能进入源码下载、成果附件、skills 或记忆；多个账号使用隔离浏览器 context/profile。API 授权成功与网站会话有效分别展示，不用一个“已连接”掩盖两种状态。

当前源码有 root `run_command`，浏览器 profile 在 bot 的 sandbox 内。因此单纯加密备份、或不在提示词展示 Cookie，都不能证明 agent 无法访问工作中的浏览器凭据。需要持久存放敏感网站身份时，应增加由服务器维护的隔离浏览器执行环境：不向通用 shell 暴露 profile 文件、原始 CDP 凭据或会话导出接口；本人接管和浏览器动作经服务端控制。开发 sandbox 可继续用于代码与文件处理。实际隔离方式需在实现前完成设计和攻击路径验证，不能以文件权限或插件提示词代替 root 工具的隔离。[当前工具能力](../../apps/api/src/agent/tools.ts)

浏览器服务按 bot/账号管理隔离 context、网络访问和工具操作，秘密导出及浏览器系统页面不向普通 agent 工具开放。认证相关任意脚本执行、截图/录屏存储和可疑 URL 跳转需结合实际工具边界验证。首期若仍在原 sandbox 使用已登录 Chrome，应明确提供的是该 bot 内的账号委托能力，不能宣称完成了上述严格凭据隔离。

这项设计限制凭据的读取、导出和跨账号使用；已授权 agent 在网页内操作仍具有账号的实际业务能力。写入授权、预览、提交记录和停止能力需要同时实现。

## 4. 任务怎样持续处理

```text
飞书消息或 Web 委托
        ↓
核验请求人 → 选定个人 bot → 保存目标、账号和操作范围
        ↓
后台 worker → 飞书 API 或指定账号的浏览器 → sandbox 文件处理
        ↓
进度与检查点 → 需要本人时发请求，其他独立工作可继续
        ↓
结果检查 → 保存成果和业务回执 → Web 展示、飞书通知
```

目标保存完整要求、验收条件、任务步骤、预算、当前执行点、账号引用与成果；不只保留一段聊天历史。worker 租约、执行记录和人工请求都持久化。浏览器和桌面操作遵守单一控制权，代码/文件等独立工作可并行；恢复执行先检查实际页面和业务状态。

发消息、提交表单、创建记录等外部操作保存已授权内容的版本、账号、目标对象和回执。重试前核查是否已经完成；无法确定时等待人处理，避免重复发送或提交。用户已授权的正常步骤直接继续，内容/收件人变化超出授权时才建立必要确认。

## 5. 具体使用场景

### 在线问卷或答题页面

1. 本人给 bot 一个页面链接和任务范围，例如打开页面、根据指定材料准备答案、填写、展示预览及是否提交。
2. bot 建立目标，检查该页面是否需要网站登录；需要时本人在对应浏览器接管登录。飞书身份仅在该网站正式支持 SSO 时用于其登录流程。
3. 读取获准材料、整理或填写；缺少必要字段时请求补充。右侧展示执行浏览器的实时画面，结果卡片显示进度和依据。当前网页 tab 用于生成服务的 iframe 预览；它不是带远端登录态的实际执行浏览器，外部网站操作应通过浏览器画面与接管入口呈现。
4. 达到已授权提交范围时执行；需要本次确认时展示填好的内容与提交对象，再继续。保存实际提交回执，不以点击成功作为完成证据。
5. 关闭 i-bot 页面后任务可继续；登录失效时保存进度并通知本人。恢复后检查是否已提交，再决定后续操作。

### 整理会议材料并通知同事

读取本人授权的文档/日程 → 确定目标与材料范围 → 用通讯录定位同事 → 生成文件或网页 → 提供预览 → 用指定的机器人或本人授权发送路径发给确定收件人 → 保存回执。通讯录在确定收件人时发挥作用，用户不必先打开组织目录。

### 持续跟进事项

本人设置关注对象、触发条件、工作范围和通知去向。定时或获准平台事件触发检查，出现有意义的变化才继续目标或通知；需要本人处理时建立请求。关闭聊天不关闭规则，用户能随时暂停、改条件、停止或撤销连接。

## 6. 界面以任务与结果为中心

- bot 页面：聊天委托、当前目标与进度、待处理请求和成果；选择本次使用的账号。
- 右侧工作区：实际网页/桌面预览、人工接管、文件；需要登录时直接进入对应环境。
- 我的连接：连接账号、账号身份、API/网页登录各自状态、允许的操作、作用 bot、重新登录、断开；详细凭据永不展示。
- 通知：需要本人登录/补充/确认、目标完成或失败；点击回到相应任务。
- 通讯录：收件人选择器和按需查询工具；部门树用于辅助找人或响应明确的组织查询。公司管理与目录浏览均为确有管理需求后的可选能力。
- 本人的外部入口配置：飞书/webhook来源、外部人员/服务、可用业务动作与资源；工具实际调用检查外部权限。本人平台与网站操作不套用外部名单，通讯录不授予同事平台访问权。

飞书卡片提供任务回执、简要进度、输入/确认与结果链接；详细网页执行预览仍由 i-bot 工作区承载。首期共用 Triage 的消息入口时由现有服务路由，不启动另一个独立接收器争用同一应用事件。

## 7. 参考个人 agent 的哪些能力

本设计参考 OpenMuse 固定版本 `d0b3a6b3ea461bc938a5dea6c46e65eefdb1b933` 的具体流程：持久委托任务、浏览器接管、已连接账号、文件副本预览、人工输入后继续、结果与通知关联；它的 Google 与真实模型集成仍有待验收范围。本轮读取固定源码资料，不声称其最新版本能力或直接复用其单 owner 身份架构。[官方功能清单](https://github.com/CopilotKit/openmuse/blob/d0b3a6b3ea461bc938a5dea6c46e65eefdb1b933/docs/FEATURES.md)、[账号授权实现](https://github.com/CopilotKit/openmuse/blob/d0b3a6b3ea461bc938a5dea6c46e65eefdb1b933/apps/server/src/google-auth.ts)、[既有核实](./openmuse-capabilities.md)

对 i-bot 的开发优先级为：持久目标及人工请求 → 账号授权和安全执行边界 → 飞书消息/任务路由 → 网页执行与预览 → 成果/回执/通知 → 更多平台能力。通讯录作为工具按需接入；首期不建设独立组织资料页面。

## 8. 必须分别验收的结果

正确识别本人和 bot；机器人/本人发信身份准确；API token 不进入 sandbox/模型/日志；账号不能跨用户使用；网页版恢复后账号正确且受控；通用 root shell 无法读取隔离浏览器的登录材料；前端关闭及后端重启后的任务恢复；授权失效与撤销；重复事件、迟到确认和不确定提交；成果下载与通知真实送达。

这些均为开发验收要求；本轮只更新设计，没有保存用户登录状态、执行答题或发送消息。
